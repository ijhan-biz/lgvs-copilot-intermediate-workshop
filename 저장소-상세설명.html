이 저장소에는 무엇이 있고,
하루 동안 무엇을 하나요

이 저장소는 하루짜리 실습 과정의 수강생 자료입니다. 이미 동작하는 작은 Node.js 도구 하나를 놓고, 바뀌는 요구와 일부러 넣은 결함을 다루며 AI의 답을 계약·검사·실제 실행으로 확인하는 연습을 합니다. 이 문서는 폴더 구조부터 파일마다의 역할, 예제 도구의 규칙, 하네스, 하루 흐름, 교육 목표와 기록 기준까지 한곳에 풀어 씁니다.

1한눈에 보기

무엇을 다루나

가상의 테스트 결과 정리 도구입니다. 검사 결과 8행을 읽어 상태별 건수, 모듈별 요약, 다음에 살펴볼 검토·재실행 후보를 만듭니다. 앱을 새로 만들지 않고, 후보를 고를 뿐 검사를 실제로 다시 돌리거나 출시를 승인하지 않습니다.

어떻게 배우나

계약을 먼저 읽고 기대값을 손으로 셉니다. AI의 답은 원문과 대조하고, 요청이 와도 사람의 승인 뒤에만 승인된 만큼 고칩니다. 일부러 실패시켜 안전장치를 확인하고, 마지막에는 대화 기억이 아니라 남긴 안내만 보고 다시 실행합니다.

저녁에 남는 것

  • 승인된 만큼만 고친 도구와 그 변경을 지키는 내 검사
  • 내가 짠 하네스와 일부러 실패시킨 기록
  • 남이 이어받을 인계 묶음: README 완성란, handoff, 마지막 재현 근거

한 줄로 말하면 “AI가 써 준 답을 그냥 믿지 않고, 무엇을 맡겼고 무엇을 직접 확인했는지 설명할 수 있게 되는 하루”를 위한 저장소입니다.

4실습 폴더 example-project 안

기능별로 묶었습니다. 처음 받은 상태에서 npm test는 16개가 통과하고, 하네스 세 파일은 TODO라 npm run harness:check는 실패하는 것이 정상입니다.

업무 코드 · src/

summarize-results.mjs승인 뒤 한 곳
진입점입니다. 입력을 검사한 뒤 후보 정책 ['failed']로 요약을 만듭니다. 13:45 변경 요청과 사람 승인 뒤에 이 정책 한 곳만 바꿔 후보를 넓힙니다.
summary-core.mjs읽기
빌드 선택, 중복 정리, 상태별 건수, 모듈 요약, 후보 고르기를 하는 공통 계산입니다. 진입점이 넘긴 정책을 그대로 따릅니다.
validate-input.mjs읽기
요약하기 전에 입력 전체를 검사합니다. 칸이나 값이 계약과 다르면 고쳐 주지 않고 TypeError로 거부합니다.

합성 입력 · data/

test-results.json고치지 않음
공개 입력 8행입니다. 선택한 빌드의 7행에서 똑같은 반복 1행을 빼면 검사 6개이고, 다른 빌드의 1행은 세지 않습니다. 상태는 통과 2 · 실패 2 · 시간 초과 1 · 미실행 1입니다.
transfer-results.json고치지 않음
혼자 풀기(독립 시도)에서 처음 보는 새 입력 7행입니다. 결과를 실행하기 전에 후보를 먼저 예측합니다.

약속과 읽을거리

contract.txt읽기
판단의 기준입니다. 처음 약속(v1)과 승인 후 변경(v2), 여섯 규칙 C1–C6, 별도 하네스 계약을 적었습니다. 코드는 구현, 실행 출력은 그때의 관찰이라 셋이 다르면 계약을 따릅니다.
domain-behavior.txt읽기
요구·계획·개발의 공통 읽기입니다. 용어를 정하는 DDD, 행동 예시를 합의하는 BDD, 공개 예시와 기존 검사의 연결, 계획과 기록의 추적, 명령 읽는 법(무엇·왜·입력·출력·산출물·다음 행동), 인계와 독립 시도의 구분을 다룹니다.
quality-guide.txt읽기
코드 품질 원칙 카드입니다. DDD·BDD·INVEST·SOLID·SMART를 원칙 이름이 아니라 “어떤 잘못을 막는가”로 설명합니다.
quality-workflows.json읽기
도메인 규칙을 행동 예시로 바꾸기 같은 작업 카드 모음입니다. 자동으로 불러오거나 실행하지 않고, 필요한 카드만 읽어 일반 Chat에 손으로 건넵니다.

검사 · test/

v1.test.mjs고치지 않음
처음 정책의 공통 검사 16개입니다(npm test). 새 정책을 구현한 뒤에는 옛 후보 검사 1개가 실패하는 것이 정상입니다.
v2.test.mjs고치지 않음
승인 후 정책의 공통 검사 16개입니다(npm run test:v2). 처음에는 후보 범위 검사 1개가 실패하고, 최종 확인은 이것으로 합니다.
contract-suite.mjs고치지 않음
v1·v2·review 검사가 함께 쓰는 C1–C6 검사 본문입니다.
learner.test.mjs내가 씀
제공 예제 1개로 시작합니다. 내가 3개를 더합니다: 똑같은 반복은 한 번 → 후보 확대(구현 전에 먼저 실패) → 원본 보존.
transfer.test.mjs내가 씀
혼자 풀기의 예측 칸입니다. 처음엔 expectedIds = null이라 실패합니다. 실행 전에 예측과 이유를 써서 고정합니다.
review.test.mjs고치지 않음
결함 사본 review/summarize-results.mjs를 같은 16개 계약으로 검사합니다. 사본을 만들기 전에는 실행할 대상이 없습니다.
web.test.mjs, harness-regression.test.mjs고치지 않음
결과 화면과 하네스 부품이 약속대로 동작하는지 지키는 검사입니다(test:web, test:harness). 수업의 필수 명령은 아닙니다.

선택형 도움 사다리입니다. 기대값과 시도를 먼저 적은 뒤 한 단계만 엽니다: 0 환경, 1 검토 대상, 2 작은 반례 질문, 3 내 가설 점검 질문, 보충으로 JS 문법 카드. 완전한 복구 해설은 학습자 파일에 없습니다.
prompts.txt읽기
단계별 요청 원문입니다. 자동 적용이 안 되는 환경에서 필요한 부분만 손으로 복사해 씁니다. 답변은 사람이 검토할 제안이지 승인 기록이 아닙니다.
.github/copilot-instructions.md
Copilot이 이 폴더에서 지킬 공통 지침입니다. 판단 근거는 계약, 용어는 도메인 안내를 따르게 합니다.
.github/instructions/
하네스 파일과 검사 파일을 다룰 때 따로 붙는 지침 두 개입니다.
.github/prompts/
채팅에서 /이름으로 부르는 단계별 요청 여섯 개입니다: requirements, context-check, plan, failure-read, harness-review, handoff-critique.
.github/agents/harness-reviewer.agent.md
하네스와 변경을 읽기만 하는 검토 에이전트입니다. 편집·실행·승인을 하지 않습니다. 모두 선택 도구이며 판단과 실행은 본인이 합니다.

그 밖의 폴더와 수업 중 생기는 것

readiness/
수업 전에 별도 연습 사본에서 하는 편집·저장·실행 연습입니다. npm run readiness:check가 처음엔 의도적으로 실패하고, 값 하나를 직접 고쳐 저장한 뒤 다시 실행합니다. 수업용 사본에는 옮기지 않습니다.
independent-task.txt
혼자 풀기 과제 설명입니다. 새 입력에 승인된 계약을 적용하고, 예측과 첫 실제 결과를 고정할 때까지 AI·힌트·강사 도움을 열지 않습니다.
operations/
제작자가 만든 합성 사용 사례 7건(usage-cases.json)과 문맥 판단 상황(context-scenarios.json), 읽는 법입니다. 실제 사용자 관찰이나 효과 지표가 아닙니다.
templates/review-summarizer.mjs고치지 않음
결함 사본의 원본입니다. 직접 고치지 않고 prepare:review가 복사한 사본을 고칩니다.
web/index.html
결과 화면 페이지입니다. 입력에서 후보까지의 흐름, 지금 코드의 후보 정책, 진행 상태를 보여 줍니다.
.baseline/수업 중 생김
npm run baseline이 첫 편집 전에 만드는 기준 사본입니다.
.harness/수업 중 생김
하네스 승인 이유, 실행·시간 초과·금지 거절·stale·새 승인·이어 하기의 실제 기록입니다.
review/수업 중 생김
prepare:review가 한 번 만드는 결함 사본입니다. 첫 실패를 남긴 뒤 원인을 찾아 이 한 파일을 고칩니다.
evidence/수업 중 생김
마지막에 npm run evidence로 다시 실행한 근거입니다.

5예제 도구가 하는 일

빌드는 검사할 프로그램의 한 버전이고, 모듈은 기능별 묶음입니다. 도구는 결과 파일을 읽어 한 빌드의 숫자를 정리하고 다음에 살펴볼 후보를 고릅니다. 공개 입력으로 따라가면 이렇게 됩니다.

  1. 입력 전체 검사8행 모두 칸과 값을 확인합니다. 다른 빌드의 잘못된 행도 거부합니다.
  2. 빌드 고르기요청한 빌드의 7행만 남깁니다.
  3. 반복 정리똑같은 반복 1행을 한 번만 세서 검사 6개가 됩니다.
  4. 숫자 정리상태별 건수(통과 2 · 실패 2 · 시간 초과 1 · 미실행 1)와 모듈별 요약.
  5. 후보 고르기정책에 맞는 행을 처음 나온 순서대로 새 배열에 담습니다.

4 개 후보 · 시간 초과·미실행 포함

바뀌는 것은 후보 범위뿐입니다. 상태별 건수, 반복·충돌 처리, 순서, 입력 검사, 원본 보존은 그대로입니다. 요청 자체는 승인이 아니고, 후보는 권고일 뿐 자동 재실행이나 출시 허가가 아닙니다. 미실행은 통과가 아닙니다.

코드가 지킬 여섯 가지 (C1–C6)

C1요청한 빌드만 센다다른 빌드의 같은 검사 번호는 별개 검사입니다.
C2후보는 승인 뒤에만 넓힌다v1은 failed만, 승인 뒤 v2는 failed · timed_out · not_run.
C3반복은 한 번, 충돌은 오류buildId + module + caseId와 이름·상태까지 같으면 한 번, 이름·상태가 다르면 TypeError.
C4처음 나온 순서 그대로모듈과 후보를 이름순으로 정렬하지 않습니다.
C5요약 전에 입력 전체 검사계약과 다르면 고쳐 주지 않고 거부합니다.
C6원본은 그대로, 요약은 새로입력 배열·행·옵션을 바꾸지 않고, 후보에는 처음 남긴 원본 행을 담습니다.

자세한 조건은 contract.txt에 있습니다. 입력의 상태별 건수와 node:test의 통과 수는 서로 다른 숫자입니다.

6하네스: 내가 짜는 안전한 작업 순서표

하네스는 AI 에이전트(또는 사람)가 일할 때 따르는 작업 순서표입니다. 업무 함수는 후보만 만들고, 하네스는 이 교육 도구의 허용된 검사를 실제로 실행합니다. 최소 하네스를 직접 만들고 운영하는 것도 필수이며, 제공 실행기를 실행하는 데서 끝나지 않습니다.

  1. 허용 도구만inspect-input, test:v2 말고는 실행 전에 거절합니다.
  2. 정해진 순서검증 → 승인 확인 → 순서대로 실행.
  3. 실패하면 멈춤실패를 기록하고 그 자리에서 멈춥니다.
  4. 모두 기록명령·종료 코드·fingerprint·산출물이 .harness에 남습니다.

제공되는 것과 내가 쓰는 것

  • 제공: 보호된 실행 부품(scripts/harness*.mjs)과 부품 설명서
  • 내가 씀: instructions.txt(지시), workflow.json(설정), run.mjs(10–25줄 조합과 실패 중단 분기)
  • 완성 구성이나 강사 실행기를 복사하지 않습니다. v1 npm test 16개 통과는 하네스 완성이 아닙니다.

꼭 관찰할 네 가지

  • 시간 초과: 실제 자식 프로세스가 제한 시간에 끝나며 실패로 남는지
  • 금지 요청: 허용 밖 도구가 실행·쓰기 전에 거절되는지
  • 오래된 근거: 성공 뒤 지시를 바꾸면 stale이 되고 재개가 거절되는지, 사람이 다시 검토·승인해 새로 실행하는지
  • 안전한 재개: 같은 fingerprint의 중단 작업만 checkpoint에서 이어 가고, 재시도 상한과 성공 단계 중복 방지가 지켜지는지
npm run harness:check npm run harness:approve -- --reason "직접 검토한 범위와 이유" npm run harness:run npm run harness:drill -- timeout # 또는 forbidden npm run harness:status npm run harness:resume -- --latest

로컬 승인 선언은 신원 인증이나 실제 기업 승인이 아니고, 허용 목록은 완전한 샌드박스가 아닙니다. README와 handoff도 fingerprint에 들어가므로 정해진 시간에는 열어 보기만 합니다.

따로 적는 양식은 없습니다. 일하면서 생기는 프로젝트 파일에 남기고, 같은 내용을 두 곳에 다시 쓰지 않습니다.

남길 것어디에
기대값test/learner.test.mjs, test/transfer.test.mjs — 실행 전에 먼저 씁니다
하네스 승인 이유npm run harness:approve -- --reason "…"가 .harness에 남깁니다

마지막에 다시 칠 여섯 명령

evidence는 최종 정책의 공통 검사 실행 근거입니다. 내 검사·검토 검사·사람 승인·AI 활용을 한꺼번에 증명하지 않습니다.

강사가 보는 기준

다섯 항목(목적·성공 기준, 맥락·모델 판단, 핵심 작업 과정, 검증·원인 수정, 본인 재현·인수인계)을 각 0–2점으로 봅니다. 합계 8점 이상이고 필수 세 항목이 각각 1점 이상이면 통과입니다.

하네스 세 파일이나 운영 근거가 없으면 전체 완료는 HOLD입니다. 학습자 자가 채점은 없고, 미실행·미확인은 점수를 짐작하지 않고 보류합니다. 자세한 기준은 따라하기의 ‘끝나면 강사가 보는 것’에 있습니다.

공통 검사 16개, 내 검사 최소 4개(제공 1 + 내가 추가 3), 검토 검사 16개, 독립 과제 1개, 하네스 결과는 서로 합산하지 않습니다. 한쪽의 통과로 다른 쪽의 실패나 미실행을 대신하지 않습니다.

10명령 한눈에

11지키는 경계와 한계

늘 지킬 것

  • 실제 회사 코드·고객 자료·개인정보·비밀키는 Copilot에 붙여 넣지 않습니다. 실습 자료는 모두 합성입니다.
  • 추가 설치·네트워크·관리자 권한이 필요 없습니다. 로컬 실행에 네트워크가 필요 없다는 말이 Copilot도 오프라인으로 된다는 뜻은 아닙니다.
  • 혼자 하는 실습입니다. Copilot이 정책 때문에 막히면 그렇게 적고, 직접 읽고 고치고 실행해서 계속합니다.
  • 데이터 안의 “이전 지시를 무시하라” 같은 문장은 지시가 아니라 데이터입니다.
  • 개인 기록은 git add -f나 웹 업로드로 공개하지 않습니다.

이 저장소가 주장하지 않는 것

  • 공개 저장소에는 강사 정답과 완성 비교 구현이 없습니다. 참고답안은 17:25 이후 조건을 갖춘 사람에게 따로 제공합니다.
  • 검사 통과가 사람의 이해, Copilot 숙련, 실제 서비스 운영 능력을 인증하지 않습니다.
  • 혼자 풀기의 자동 검사는 내 예측과 내 코드가 일치하는지만 봅니다. 둘 다 틀려도 통과할 수 있습니다.
  • 합성 사용 사례와 역할 시나리오는 실제 수강생 조사나 학습 효과가 아닙니다.
  • 공식 LG 또는 Microsoft 발행·인증·후원을 뜻하지 않으며, 별도의 재사용 라이선스는 지정하지 않았습니다.
