소스 품질 원칙 — 기존 실습에 적용하는 짧은 카드
===============================================
추가 패키지 설치나 실습 범위 확장은 하지 않습니다.
자세한 비교와 공개 출처는 워크북(읽기 안내서)의 ‘코드 품질 원칙’ 절을 봅니다.
요구·계획·개발에서 먼저 적용하는 용어/행동/실제 검사 연결은 domain-behavior.txt를 봅니다.
이 카드는 그 흐름을 보조하며 별도 테스트·제출 양식이 아닙니다.
원칙 이름보다 “어떤 잘못을 막는가”를 봅니다. 같은 검사와 후보의 뜻을 정한 뒤 행동 예시로 확인하고,
지금 승인된 작은 변경에 필요한 원칙만 씁니다. 근거와 기각 이유는 README 변경이유와 handoff에 짧게 둡니다.

DDD = Domain-Driven Design (도메인 주도 설계)
‘빌드·모듈·검사 구분·원본/고유/중복 건수·상태·검토 후보’의 뜻을 합의합니다.
집계·후보·중복·순서·입력 검증·원본 보존을 도메인 규칙으로 설명하고 입력 검증·순수 계산·IO의 책임을 구분합니다.
이 작은 결과 정리 함수에 Aggregate·Repository·마이크로서비스를 억지로 만들지 않습니다.
후보 보고는 실제 검사 재실행이나 출시 승인과 다른 업무입니다.

YAGNI
13:45 변경 요청 공개와 사람 승인 뒤에는 failed 후보에 timed_out과 not_run을 추가하는 변경만 필요합니다.
자동 재실행·UI·DB·플러그인·새 패키지는 실제 필요와 승인이 있기 전까지 보류합니다.
필수 입력 검증·보안·경계·회귀 테스트를 없애는 것은 YAGNI가 아닙니다.

클린 코드
이름으로 의도를 설명하고, 전체 검증·중복 정리/집계·파일 IO의 책임을 구분합니다.
오류를 0건 요약으로 숨기거나 원본을 정렬하지 않습니다. 첫 원본 행 참조 보존 계약을 유지합니다.
리팩터링은 필요한 가독성 개선만 하고 동작 유지와 회귀를 확인합니다.
코드 길이·추상화 개수·커버리지 숫자만으로 품질을 판정하지 않습니다.

BDD와 TDD
BDD = Behavior-Driven Development(행동 주도 개발).
업무·개발·QA 관점의 질문으로 예시를 발견하고 → Given/When/Then으로 행동을 합의하고 →
독립 기대 단언을 기존 node:test로 자동화합니다. Given/When/Then만 쓰면 끝나는 것이 아닙니다.
개인 실습에서는 관점별 질문을 스스로 점검합니다. 가상 참석자/회의를 실측처럼 만들지 않습니다.
Cucumber 설치는 필요 없습니다. 실제 검사 제목·공개 정상/중복/오류/빈 결과/보존 예시는
domain-behavior.txt 3절에 있으며 테스트의 기대값과 실제 실행 증거를 연결합니다.
TDD: 필요한 행동을 검출하는 RED → 최소 구현 GREEN → 필요하면 동작 유지 리팩터링.
요구 변경과 구현의 기존 후보 확장 테스트를 다음과 같이 읽습니다. 중복 테스트를 추가하지 않습니다.
Given 선택 빌드에 timed_out과 not_run 검사 결과가 있다.
When 후보 확대를 사람이 승인한 후 해당 빌드를 요약한다.
Then 두 상태를 후보에 포함하며 상태별 건수는 그대로다.
기대값은 계약에서 계산합니다. 현재 구현이 반환한 값을 복사하지 않습니다.
결과와 기준 검증에서는 기존 테스트가 잡는 오동작과 기대값의 계약/입력 근거를 expected에,
실제 관찰을 execution에, 검증하지 못한 한계를 unknown에 연결합니다. 새 테스트·표·점수는 없습니다.
인계 요약에도 not_run 건수와 중복 정책을 남깁니다. 문장 편집으로 옛 증거가 새 실행이 되지는 않습니다.

검토 질문
1. 이 이름과 조건은 어떤 도메인 규칙을 나타내는가?
2. 지금 필요하지 않은 기능·추상화·의존성을 만들고 있지 않은가?
3. 변경 책임·실패 조건·부작용이 드러나는가?
4. 테스트가 요구를 검출하는가, 현재 구현을 따라 적은 것인가?
5. 실제 실행 근거와 미확인 부분이 구분되는가?
6. 근거 부족으로 보완을 기다릴지, 전문가 검토·핵심 영향 검토·사전 허용 정형 검토 중 무엇이 필요한가?

이 카드는 수동 참고 자료입니다. 네이티브 GitHub 스킬 자동 탐색 파일이 아닙니다.
스킬의 승인 요청·허용 파일·명령·데이터 경계와 실제 실행 결과는 사람이 확인합니다.

SOLID / INVEST / SMART는 서로 다른 질문
SOLID는 코드 책임·변경 의존성을 본다. validate-input의 검증, summarizeTestResults의 도메인 계산,
usage-probe의 로컬 입력/관찰 어댑터를 구분한다. 작은 함수에 패턴·계층을 늘리는 과제가 아니다.
INVEST는 작업의 독립성·협의 가능성·가치·추정/크기·검증 가능성을 본다.
관련된 원인 재현→복구→회귀는 하나의 결과 경계다. 무관 작업 충돌은 소유자·인터페이스로 나눈다.
SMART는 목표의 구체성·측정·달성 가능성·관련성·기한을 본다.
예: 기존 demo 슬롯에 내 예측과 합성 ID/상태를 대조하고 다음 질문을 기록한다.
이 목표 달성은 사용자 만족·운영 준비·숙달 측정이 아니다. 실제 피드백은 아직 없다.
고정 70% 문맥 규칙·기능마다 새 세션·전체 재작성/병렬 전면 금지를 보편화하지 않는다.
수정과 재검증의 changeReason과 최종 비판에는 기각 이유·재검토 조건을 같은 기록에 연결한다.
예: not_run을 passed로 세는 대안은 미실행과 통과를 구분하는 상태 의미를 어긴다. 그 의미가 승인 변경되면 재검토할 수 있다.
현재 맥락의 판단이지 영구 금지나 별도 실패 일지·스킬 카드 과제가 아니다.

작은 실험과 반복 개선
operations/usage-cases.json은 소스 실험 입력, context-scenarios.json은 문맥 판단 사실이다.
내 expected를 먼저 고정하고 실제 execution과 불일치 이유를 확인해 다음 승인 변경으로 잇는다.
합성 수치와 모델 판단은 실제 사용자 관찰이 아니다. 테스트 GREEN은 운영 충분조건이 아니다.
안전한 노출 제안은 책임자/권한·관찰·중단·복구가 묶여야 한다. API/DB/retry/롤백 구현은 보류한다.
남은 제품 질문·알려진 로컬 복구·미검증 운영 복구를 기존 unknown/nextAction에 구분한다.
