도메인에서 행동 검증까지 — 요구·계획·개발의 공통 읽기
====================================================
필수 하네스와 업무 함수의 경계
-----------------------------
업무 함수는 입력 기록을 요약하고 후보만 만든다. 실제 제품 검사를 재실행하지 않는다.
학습자는 별도로 harness/workflow.json·run.mjs·instructions.txt를 직접 작성한다.
하네스는 제공 부품으로 이 교육 도구를 검사하는 허용 작업을 실제 실행하고 실패에서 멈춘다.
예를 들어 입력의 timed_out 1건은 과거 합성 상태다. 하네스 timeout 훈련은
지금 자식 프로세스가 제한 시간에 종료되는지 보는 실제 관찰이다. 같은 숫자로 세지 않는다.
workflow에는 목적·입력/맥락·허용 도구·출력·시간/재시도 한도를, run에는 순서·기록·중단을,
instructions에는 허용/금지 작업·출처·사람에게 반환할 조건을 본인이 쓴다.
금지 도구는 실행 전에 거절한다. 성공 뒤 지침이 바뀌면 옛 근거는 stale이며 재개하지 않는다.
동일 fingerprint 중단 작업만 checkpoint에서 이어 가고 재시도 상한·성공 효과 중복 방지를 확인한다.
변경된 파일은 사람이 다시 검토·승인한 새 실행으로 확인한다. 로컬 선언은 기업 권한 인증이 아니다.
이 구축·운영도 아래 규칙→예시→예상 실패→실제 근거 흐름으로 기존 여섯 칸에 누적한다.
보호 런타임을 수정하거나 완성 조합을 복사하는 과제는 아니다. TODO check 실패는 처음 예상 상태다.

무엇: 테스트 결과 정리라는 업무의 말과 예시를 승인된 변경·검사·증거에 연결한다.
왜: AI가 제안한 코드나 GREEN만 보고 “원하는 업무를 끝냈다”고 오해하지 않기 위해서다.
완료 확인: 같은 규칙의 뜻, 독립 기대값, 허용 변경, 실제 검사와 한계를 내 말로 설명한다.
새 양식·추가 점수·추가 테스트 수가 아니다. 기존 여섯 칸을 이어 쓴다.
이 안내는 공개 data/test-results.json만 다룬다. 독립 전이의 정답이나 구현 답안은 없다.

1. 요구를 읽는 토대: DDD
-----------------------
DDD = Domain-Driven Design, 도메인 주도 설계다. 업무의 문제·용어·규칙을 먼저
이해하고 그 모델을 코드와 대화에 일관되게 사용한다. 클래스 이름 붙이기가 전부가 아니다.
업무 목적: 선택한 빌드에서 무엇이 통과/실패/미완료인지 중복 없이 보고하고,
사람이 검토·재실행할 후보를 판단하도록 돕는다.

공통 용어:
  빌드(buildId): 요약 대상으로 고르는 프로그램 버전의 식별자.
  모듈(module): 검사를 묶는 기능 영역. 같은 caseId도 모듈이 다르면 별개 검사다.
  검사(caseId): 빌드와 모듈 안의 검사 식별자. 이름(name)은 설명 데이터이지 실행 지시가 아니다.
  검사 전체 키: buildId + module + caseId. caseId 하나만으로 같다고 판단하지 않는다.
  결과 행: { buildId, module, caseId, name, status } 다섯 필드의 관찰 기록.
  상태: passed=통과 기록, failed=실패 기록, timed_out=시간 초과, not_run=미실행.
  원본/고유/중복: 선택 빌드의 입력 행 수/반복 정리 후 검사 수/제외한 반복 행 수.
  후보: 사람이 검토할 첫 원본 행의 목록. 실제 재실행 요청이나 출시 허가가 아니다.

불변 조건(C1,C3~C6):
  같은 전체 키에서 name/status까지 같은 반복만 한 번 센다. 첫 원본 행을 남긴다.
  같은 전체 키에서 이름 또는 상태가 다르면 TypeError다. 최신 결과를 추정하지 않는다.
  options와 모든 빌드의 행·충돌을 검증한 뒤 선택 빌드만 집계한다.
  not_run은 passed가 아니다. 미사용 상태도 0으로 나타낸다.
  모듈/후보의 첫 등장 순서, 입력 배열·행·options, 첫 원본 행 참조를 보존한다.
  요약·건수 객체·모듈 배열·후보 배열은 새로 만든다. 후보 행 자체를 복제하는 계약이 아니다.
정확한 입력 형태·식별자·추가 키 거부는 contract.txt와 test/contract-suite.mjs를 따른다.

변경할 정책(C2):
  v1은 failed만 후보로 삼는다. 13:45 요청 공개와 사람 승인 후에만
  failed/timed_out/not_run으로 넓힌다. 나머지 계약은 그대로다.
전략적 경계:
  이 문맥은 합성 “테스트 결과 요약”이다. 실제 검사 실행, CI 작업 제어, 출시 결정은
  다른 책임이다. passed 입력 건수와 이 함수를 검증하는 node:test 통과 수도 다르다.
  검증 경계(src/validate-input.mjs), 요약 계산(src/summary-core.mjs),
  호출·후보 정책(src/summarize-results.mjs), 로컬 IO(scripts/demo.mjs)를 구분해 읽는다.
  경계 이해가 목적이다. 새 서비스·Entity·Aggregate·Repository를 만들 필요는 없다.

2. 행동을 합의하는 토대: BDD
---------------------------
BDD = Behavior-Driven Development, 행동 주도 개발이다. 업무 관점의 질문으로
규칙과 예시를 발견하고, 구체적으로 합의한 행동을 실행 가능한 검사로 연결한다.
Given/When/Then 문장만 적거나 나중에 테스트 이름을 바꾸는 것으로 끝나지 않는다.
Cucumber나 새 패키지는 설치하지 않는다. 기존 node:test로 검증한다.

발견(discovery) — 개인 실습에서는 아래 세 관점을 스스로 질문한다.
실제로 참석하지 않은 기획자·개발자·QA와 회의했다고 기록하지 않는다.
  업무 관점: 후보를 보고 누가 무엇을 판단하는가? 미실행을 빼면 어떤 정보가 사라지는가?
  개발 관점: 같은 검사의 키는 무엇인가? 후보만 바꿀 때 어떤 계약을 유지해야 하는가?
  QA 관점: 정확한 반복과 충돌은 어떻게 다른가? 선택 밖 빌드의 충돌도 거부하는가?
대답이 계약에 없거나 서로 충돌하면 미확인으로 남기고 승인 전에 확인한다.

구체화(formulation) — 아래 공개 예시에서 Given(전제)/When(행동)/Then(관찰 결과)을
내 말로 설명한다. 기대값은 계약과 입력을 읽어 먼저 구한다. 함수 실행값을 복사하지 않는다.
자동화(automation) — 해당 node:test의 단언을 읽고 무엇을 놓칠 수 있는지도 설명한다.
요구 변경은 내 판별 테스트 RED → 승인 범위 최소 구현 → GREEN → 전체 회귀 → 증거 확인이다.
오전 중복 검사와 오후 C6 검사는 유지 조건 확인이다. 계획 단계에는 새 구현/테스트를 쓰지 않는다.

3. 공개 예시와 기존 검사 연결
---------------------------
아래 경로는 모두 example-project 기준이다. C 번호는 contract.txt의 규칙이다.
각 예시는 기존 공통 16개 안의 검사를 가리키며 별도 제공/본인 검사 수로 더하지 않는다.
검사 제목은 test/contract-suite.mjs의 실제 제목이다. v1은 npm test,
승인 후 최종 계약은 npm run test:v2로 실행한다. 증거 경로는 5절을 따른다.

정상/후보 변경 C1,C2
  Given 공개 8행과 { buildId: 'BUILD-DEMO-1' }.
  When 현재 승인 버전으로 요약한다.
  Then 원본7/고유6/중복1, counts={passed:2,failed:2,timed_out:1,not_run:1},
       모듈 media → connectivity → settings다.
       v1 후보는 media/TC-102 → connectivity/TC-101.
       승인 후 v2는 media/TC-102 → media/TC-103 → connectivity/TC-101 → connectivity/TC-202.
  독립 단언: 전체 건수 객체와 순서 있는 후보 목록을 정확히 비교한다.
  연결 검사: C1 | 요청 빌드의 원본·고유·중복·상태·모듈 건수
             C2-v1 | 승인된 후보 상태만 포함, 미실행은 통과 아님
             C2-v2 | 승인된 후보 상태만 포함, 미실행은 통과 아님
  C2 검사는 네 상태의 별도 합성 행으로 정책을 판별한다. 공개 파일 전체 건수 검사는 C1이다.
  허용 변경: 승인 후 src/summarize-results.mjs의 후보 정책만. 본인 단언은 test/learner.test.mjs.
  관찰: 시작본 v1은 16 통과, v2는 C2-v2만 실패(15 통과/1 실패). 승인 구현 후 반대 정책의
        C2-v1 실패는 정상이다. 최종 v2 16 통과를 확인한다. 기대값/공통 검사는 고치지 않는다.

정확한 반복 C3
  Given 공개 행 2와 7(1부터 세기)은 전체 키·이름·상태가 같은 media/TC-102다.
  When 두 행만 같은 빌드로 요약한다.
  Then 원본2/고유1/중복1, failed1, 나머지 상태0, 후보 하나는 첫 행과 같은 참조다.
  독립 단언: 건수와 후보 길이/내용을 정확히 비교하고 첫 행은 strictEqual로 확인한다.
  연결 검사: C3 | 정확한 반복은 한 번, 첫 원본 참조 유지
  공통 검사는 같은 원리를 반복 3행으로 확인한다. 공개 예시의 행 수와 혼동하지 않는다.
  허용 변경: 오전 test/learner.test.mjs의 본인 반복 검사. 후보 구현은 아직 변경하지 않는다.
  관찰: v1/v2 모두 이 규칙은 GREEN이어야 한다. 후보 확대의 판별 근거는 아니다.

충돌/오류 C5,C3
  Given 공개 행 8(BUILD-DEMO-2)과 그 복사본에서 status만 failed로 바꾼 두 행.
        원본 공개 파일은 편집하지 않는다. name만 다르게 한 경우도 같은 충돌 규칙이다.
  When BUILD-DEMO-1을 요청한다.
  Then 선택 밖 빌드라도 같은 전체 키의 모순이므로 TypeError다. 0건 정상 결과가 아니다.
  독립 단언: assert.throws의 오류 형식 TypeError와 오류 후 입력 보존을 확인한다.
  연결 검사: C5/C3 | 다른 빌드까지 검증하고 이름·상태 충돌은 TypeError
  허용 변경: 계약/validator/공통 검사는 변경하지 않는다. 실패 조사 뒤 승인한 review 복구는
             review/summarize-results.mjs만 대상으로 삼는다. templates는 복구 대상이 아니다.
  관찰: 충돌을 조용히 무시하거나 “마지막 상태”로 바꾸면 이 규칙 위반이다.

빈 입력/일치 없음 C3
  Given [] 또는 공개 행 8만 있는 입력.
  When BUILD-DEMO-1을 요청한다.
  Then 원본/고유/중복과 네 상태 모두0, modules/rerunCandidates는 새 빈 배열이다.
  독립 단언: 빈 요약 전체를 deepEqual로, 반복 호출의 새 객체/배열은 notStrictEqual로 확인한다.
  연결 검사: C3 | 빈 입력·일치 없음은 모든 상태 0과 새 빈 배열
  허용 변경: 공통 검사/정상 0건 계약 유지. 오류를 0건으로 숨기는 변경은 허용하지 않는다.
  관찰: 정상적인 “해당 빌드 없음”과 잘못된 입력의 TypeError를 구분한다.

입력·순서·참조 보존 C4,C6
  Given 공개 8행, 옵션, 실행 전 값 사본과 각 행의 참조.
  When 요약한다.
  Then 입력 값·순서·옵션과 각 행 참조는 그대로다. 후보 배열은 새것이며 첫 원본 행을 가리킨다.
  독립 단언: 입력 전체 deepEqual + 각 행 strictEqual + 새 후보 배열 notStrictEqual.
             값이 같은 복사 행을 반환하는 것과 원본 참조를 반환하는 것은 다르다.
  연결 검사: C4 | 후보 첫 등장 순서와 반복 뒤 원본 참조
             C6 | 입력 배열·행·옵션 보존과 첫 후보 원본 참조
             C6 | 동결한 여러 모듈 입력·행·옵션에서도 원본 참조
             C6 | 반복 호출의 요약·건수·그룹·배열은 독립
  허용 변경: 오후 test/learner.test.mjs의 본인 C6 검사. 입력/공통 검사/출력 구조는 보존한다.
  관찰: every()만으로는 빈 후보를 놓친다. 길이·정확한 내용·순서·참조를 함께 확인한다.
        상수 true, 테스트 삭제, 기대값 완화로 GREEN을 만들지 않는다.

4. 계획과 여섯 칸의 추적 — 새 제출 양식 아님
-----------------------------------------
추적 순서: 도메인 용어/규칙 → 합의 예시 → 허용 파일/보존 계약 →
           정확한 검사 제목·명령 → 예상 관찰 → 실제 증거 상대 경로.
공개 C2 계획 예(실행/승인 완료 기록이 아님):
  후보 범위 C2 → 공개 8행의 후보2→승인 후4 예시 → 승인 후 src/summarize-results.mjs만
  변경, C1,C3~C6 유지 → “C2-v2 | 승인된 후보 상태만 포함, 미실행은 통과 아님”,
  npm run test:v2 → 변경 전 해당 단언1 실패/변경 후 공통16 통과 예상 →
  execution의 해당 실행 참조 및 실제 생성한 evidence/v2-<시각>-<uuid>.json.
  본인 후보 단언은 test/learner.test.mjs에서 RED/GREEN을 별도로 기록한다.
  이 증거 파일은 v2만 재실행하므로 본인 검사 결과를 대신하지 않는다.
기존 주 기록에 다음처럼 배치한다. README 완성란/handoff는 이 위치를 참조한다.
  purpose: “후보=C2, 사람이 후속 검토할 목록; 실제 재실행은 범위 밖”.
  expected: 위 공개 예시 중 관련 Given/When/Then, 직접 계산한 기대값·이유,
            연결한 실제 검사 제목과 예상 실패/통과. 실행보다 먼저 작성·저장한다.
  changeReason: 합의/미확인 질문, 13:45 이후 실제 사람 승인 시각·범위,
                src/summarize-results.mjs 변경과 C1,C3~C6 보존 계획. 거절/보류 이유도 둔다.
  execution: 실행 위치·Node 버전·정확한 명령·시각·exit·실제 수·단언과 증거 상대 경로.
  unknown: CI/출시/실제 Windows 실행/AI 사용 등 확인하지 않은 것은 미확인으로 남긴다.
  nextAction: 승인 대기, 원인 재현, 허용 범위 수정, 재검사, 인계 등 다음 한 행동.
상세 PLAN/runs 필드를 쓰더라도 같은 내용을 두 번 입력하지 않는다. 완료 여부는 실제 근거로 판단한다.
INVEST는 가치 있는 스토리의 크기·협의·검증 가능성을, SOLID는 코드의 변경 책임·계약을,
SMART는 이번 과업의 구체적인 완료·측정·기한을 돕는다. DDD의 업무 모델이나
BDD의 발견·합의·검증을 대신하지 않으며 셋을 하나의 AI 세션 규칙으로 합치지 않는다.

5. 명령을 읽는 법 — 무엇/왜/입력/출력/산출물/다음 행동
---------------------------------------------------
모든 명령은 Node >=22의 example-project 터미널에서 실행한다. npm install은 없다.
Windows 네이티브에서도 같은 npm 스크립트를 쓰며 WSL을 요구하지 않는다.
이 안내/제작자의 macOS 실행은 실제 Windows 실행 증거가 아니다.

npm run preflight
  Node 버전을 확인하고 범위/수동 점검 질문을 출력한다. 입력은 현재 Node 런타임이다.
  기대는 Node >=22에서 exit0, 생성 파일은 없다. 폴더·필수 파일·Copilot 권한은 자동 검사하지 않는다.
  다음은 사람이 위치/파일/계정 정책을 확인하는 일이다. 오류 시 기능 수정 대신 위치/Node부터 확인한다.
npm test (또는 npm run test:v1)
  시작 정책을 확인한다. 입력은 현재 src와 공통 계약 검사/공개 자료, 기대는16 통과/exit0다.
  콘솔 결과를 execution에 참조한다. 실패하면 시작 상태를 조사한다. 첫 편집보다 먼저 baseline이다.
npm run baseline
  변경 전 비교 근거를 보존한다. 입력은 scripts/scoped-files.mjs에 선언된 업무·기록·하네스 허용 파일이다.
  .baseline/manifest.json과 같은 상대 경로 사본을 처음 생성한다. 실제 파일을 열어 확인한다.
  이미 있으면 거부가 정상이다. 삭제/재생성/덮어쓰기하지 않는다. 확인 뒤에만 첫 편집을 한다.
npm run test:learner
  본인이 합의 예시를 판별하는지 확인한다. 입력은 본인이 작성한 test/learner.test.mjs와 src다.
  처음 제공1 → 오전 반복 추가2 → 승인 후 후보 추가3(RED→GREEN) → 오후 C6 추가4.
  콘솔 실제 수·exit·실패 단언을 execution에 연결한다. 제공1은 본인 작성으로 세지 않는다.
npm run test:v2
  승인 후 보존 계약까지 회귀 확인한다. 같은 공통16의 최종 정책 검사다.
  시작본은 C2-v2 하나 실패, 승인 구현 후16 통과/exit0가 기대다. 콘솔을 확인한 뒤 증거를 수집한다.
  실패가 단언인지 문법/import/경로 오류인지 구분한다. 계획 단계에는 실행/수정을 추가하지 않는다.
npm run prepare:review / npm run test:review
  지정 review 단계에 처음 한 번만 템플릿에서 별도 review/summarize-results.mjs를 만든다.
  이어 test:review는 그 사본에 같은 v2 계약16을 실행한다. 첫 실패를 관찰·보존한 뒤 원인을 재현한다.
  승인 복구 뒤16 통과가 기대다. 이미 있는 review를 준비 명령으로 덮어쓰지 않는다.
npm run demo
  공개 입력과 operations/usage-cases.json 7건을 현재 소스로 요약해 판단 질문을 확인한다.
  콘솔 후보/건수/오류를 독립 기대값·승인과 비교한다. CI 실행/실사용 UX 검증 산출물이 아니다.
npm run evidence
  현재 v2 검사를 실제 재실행하고 evidence/v2-<시각>-<uuid>.json을 새로 생성한다.
  입력은 현재 v2 검사·고정 허용 파일·실행 도구다. v2만 수집하며 learner/review/전이는 수집하지 않는다.
  JSON을 열어 tests=passed=16, 나머지0, testExitCode=collectorExitCode=0,
  status=passed와 전후 해시 동일을 함께 확인한다. 그렇지 않으면 이유를 남기고 완료를 보류한다.
  원시 콘솔은 저장하지 않으므로 실패 단언은 해당 테스트 명령에서 최소한만 기록한다.
npm run compare:baseline
  같은 허용 파일의 변경 해시를 요약한다. .baseline과 현재 파일이 입력이며 자동 복구는 없다.
  다음은 VS Code에서 같은 상대 경로 사본/현재의 행 비교다. 범위 밖 차이를 승인 없이 지우지 않는다.

6. 인계와 독립 전이는 구분한다
-----------------------------
인계는 기존 handoff.txt와 README 완성란에서 4절의 기록/증거 위치를 짧게 참조한다.
최종 본인 재현은 preflight → test:v2 → test:learner → test:review → demo → evidence의
기존 여섯 명령이다. v2/review16, learner 제공1+본인3=4를 따로 확인한다.
독립 전이는 independent-task.txt의 지정 시간·허용 자료만 따른다. 이 안내는 새 도움 허가가 아니다.
예측·이유·expectedIds의 실행 전 저장/동결과 최초 실제 outcome/exit/출력 저장/동결을
모두 마칠 때까지 AI·힌트·강사 도움·답안·고급 모델을 열지 않는다. 첫 예측을 덮어쓰지 않는다.
미실행은 unknown/exit null + incomplete/HOLD로, 확인한 실패는 fail로 남긴다.
도움 상태와 실제 결과는 별개다. 전이1은 learner4/공통16/여섯 명령에 합산하지 않는다.
