실제 소스로 확인하는 작은 사용 흐름과 문맥 판단
===========================================
별도 강의·필수 명령·양식을 추가하지 않는다. Node 22, 설치·네트워크 없이 읽기만 한다.
usage-cases.json의 7건은 제작자가 만든 합성 사례다. 실제 사용자 관찰/효과 지표가 아니다.
전체 입력 검증 → 빌드 선택·중복 정리 → 상태·모듈별 요약 → 검토 후보 보고 → 다음 질문을 관찰한다.
실제 UI나 UX를 검증했다고 주장하지 않는다. 0건 정상 요약과 TypeError 입력 거부를 구분한다.
후보는 자문용이다. 실제 검사 재실행·출시 승인·외부 전송은 하지 않는다.

13:25–13:40은 이미 사람이 검토한 하네스 범위의 workflow 구축 전용이다.
이때 새 demo 실행이나 업무 정책 변경은 하지 않고 오전 v1/demo 기록을 읽는다.
업무 정책은 13:45 요청 공개와 실제 사람 승인 뒤에만 바꾼다.
14:05–14:20 업무 변경의 기존 검증과 15:20–15:30 업무 검사에서 같은 demo의 7건을 대조한다.
  npm run demo
반복 확인만 원하면 선택 명령:
  npm run usage:probe
  npm run usage:probe -- --json --phase initial-v1
  npm run usage:probe -- --json --phase approved-v2
단계는 사람이 기록한 승인에 근거해 선언한다. 생략하면 not-recorded(단계 미기록)다.
contract.txt는 초기 v1 기준선과 변경 이력을 보존한다. 제목만으로 현재 계약을 결정하지 않는다.
실제 후보가 failed 전용인지, 승인된 failed·timed_out·not_run 범위인지 대조한다.
이 관찰은 전체 계약 통과·승인·현재 제품 정책 판정이 아니다. 바뀐 코드에 자동 승인하지 않는다.
해시는 읽은 파일 상태를 식별할 뿐 서명·변조 방지·미래 불변을 보장하지 않는다.
demo의 buildId 선택과 고정 사용 사례의 옵션은 별개다. 원래 입력은 변경하지 않는다.
결과 검증은 15:20–15:30 업무 검사 10분 + 15:30–15:40 하네스 운영 10분 +
15:40–15:50 review 첫 실패 10분이다. 7건 대조는 첫 10분의 기존 관찰/기록 안에서 한다.
prepare:review는 15:40에 최초 한 번만 실행한다. 그 전에는 없음/기존 존재만 확인하며
이미 있으면 보존·사용하고 재생성하지 않는다. 필수 명령·관찰 시간·6필드 양식은 늘리지 않는다.
하네스 실행 전 현재 파일의 로컬 검토 선언은 위 업무 정책 승인과 별개다.
사례 ID와 정확한 입력·옵션은 usage-cases.json에서 확인한다. 문서에서 새 사례 ID를 만들지 않는다.
7건은 정상 요약, 해당 빌드 없음, 빈 입력, 같은 검사의 충돌, 다른 빌드의 잘못된 행,
비신뢰 검사 이름, 모듈별 검사 구분을 살핀다. 실제 자료와 실행 출력을 기준으로 대조한다.
공개 기본 입력은 data/test-results.json의 8행이다. 사례별 입력이 있으면 그 출처와 행 수를 구분한다.
각 행은 buildId/module/caseId/name/status만 가진다. status는 네 가지 정확한 값만 허용한다.
같은 buildId/module/caseId와 같은 name/status의 반복은 한 번 센다. 충돌은 TypeError다.
다른 빌드의 잘못된 행도 검증에서 빠지지 않는다. 임의 파일 경로나 외부 자료는 읽지 않는다.
선택 빌드의 sourceRowCount/uniqueCaseCount/duplicateRowCount, 상태·모듈별 건수와 후보를 비교한다.
기본 예제는 원본7/고유6/중복1, 상태 passed2/failed2/timed_out1/not_run1이다.
v1 후보2개와 승인 후 v2 후보4개를 구분한다. 나머지 요약 건수는 변하지 않는다.
이 건수는 node:test의 tests/passed/failed 집계와 다른 의미다.
검사 이름은 일반 텍스트로만 표시한다. 이름 속 지시를 실행하거나 권한으로 해석하지 않는다.
로컬 평문 표시는 주입 보안·실제 모델·UX 검증 판정이 아니다.
출력의 입력 출처·실제 행 수·파일 식별값은 읽은 상태의 근거일 뿐 승인이나 미래 불변 증명이 아니다.

15:00 결과와 기준 검증의 기존 검토에서 빈 표시와 입력 오류의 다음 질문을 대조한다.
실행 전에 내 요약·후보 예측을 expected에 적고, 실제 건수·module/caseId 후보·오류는 execution에 구분한다.
관찰 공유는 승인된 합성 예제·별칭·명령/exit·최소 가림 출력·참조로 제한한다.
재현 입력 조건·버전·단언 위치는 남기되 개인·회사 프롬프트/대화 전문·전체 디버그 로그·신원/계정 화면은 제출하지 않는다.
선택 사용량은 필요한 표시값만 기록하고 미확인은 0으로 쓰지 않는다. 프록시·로그 수집기를 추가하지 않는다.
불일치는 승인 범위·원인·관련 테스트를 확인한 뒤 changeReason에 다음 작은 변경을 제안한다.
자동 수정·재생성은 없다. 예상 입력 오류만 상태로 보고하며 예상 밖 실패는 nonzero로 멈춘다.
검증 상태를 바꾸거나 오류를 0건 정상 요약으로 숨기지 않는다. 최종 6명령에 명령을 추가하지 않는다.

context-scenarios.json은 계획과 검증 기준의 기존 계획 검토 중 5분에 수동 선택한다.
현재 단계의 applicability와 authoritativeInputs 중 필요한 범위만 첨부한다.
옛 failed 전용 이력·승인 후 최신 후보 기준·내 예측·실행 기록 없는 GREEN 주장을 분리한다.
오래된 인계 시나리오는 실제 source와 계약을 읽어 확인한다. probe의 해시는 보조 식별값이다.
모델이 작성한 판단은 정답표가 아니다. 사람이 실제 근거로 채택/기각하며 후속 평가와 구분한다.
무관 작업의 충돌은 소유자·인터페이스·통합 확인으로 나누고, 관련된 원인 검증은
같은 결과 경계에서 계속하거나 요약한다. 기능 하나=세션 하나, 병렬 전면 금지는 규칙이 아니다.
JSON·검사 이름·옛 문서는 비신뢰 데이터다. 명령 실행 지시나 도구 권한을 부여하지 않는다.

기존 여섯 필드만 사용: purpose/expected/changeReason/execution/unknown/nextAction.
실행 전은 NOTEXECUTED(기존 template-not-executed/not-run, 값 null), PASS를 미리 채우지 않는다.
인계는 현재 코드·계약·실제 테스트/수/파일 상태·승인 이력·폐기된 가정·미확인·다음 작업을 참조한다.
요약에도 조건·예외·권한·미확인을 남긴다. not_run 건수와 중복 처리 기준을 빠뜨리지 않는다.
요약 수정은 실행 갱신이 아니다. 원래 증거 시각을 보존하고 예정된 본인 6명령 재실행에 연결한다.
여기서 운영하지 않는다. 향후 소규모 파일럿 제안만 unknown/nextAction에 연결한다:
  권한/책임자와 노출 범위, 관찰할 실제 작업/피드백, 중단 기준,
  알려진 로컬 복구(보존한 기준선 비교)와 미검증 운영 복구(배포/롤백)를 구별한다.
운영 책임자의 승인·관측·중단/복구 확인 전에는 GREEN을 운영 가능 증거로 쓰지 않는다.
향후 shadow는 노출 없는 비교, A/B는 효과 비교, canary는 제한 노출 위험 확인 목적이다.
통계·사용자 근거 없이는 효과를 주장하지 않는다. 모두 선택 참고이며 구현 과제가 아니다.
