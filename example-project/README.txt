GitHub Copilot 중급과정
Agentic SDLC with Github Copilot.
2026-10-28 · 09:00–18:00 제안 · 1인 1프로젝트
============================================================
현재 필수 범위 — 하네스 직접 구축과 운영
---------------------------------------
업무 함수의 후보 정책 변경과 별도로, harness/instructions.txt·workflow.json·run.mjs를
직접 작성한다. 아래 기존 업무 과제는 그대로 하되 활동 시간을 교체한다. 추가 장문 양식은 없다.
시작본 업무 v1의 npm test 16개 통과와 TODO 하네스의 harness:check 실패는 함께 예상된다.
완료 파일이나 강사 실행기를 복사하지 않는다. 제공 보호 부품의 조합과 실패 중단 분기는 본인 몫이다.
첫 편집 전 baseline은 JSON·instructions·기록에도 적용된다. 문제와 성공 기준 단계에서 남긴 기준선을 덮어쓰지 않는다.

직접 작성할 내용:
  instructions: 맥락 출처·허용/금지 작업·중단하고 사람에게 반환할 조건.
  workflow: 목적·입력/맥락·허용 도구·출력·timeout·재시도 상한.
  run: 제공 부품으로 검증→승인 확인→순서 실행→기록→실패 중단/마무리 약 10–25줄.
보호 런타임·공통 검사·데이터·package.json은 편집하지 않는다. 임의 셸·네트워크·설치는 없다.
허용 목록은 완전한 샌드박스가 아니다. 학습자 코드는 로컬 Node 사용자 권한으로 실행된다.
업무 함수는 후보만 만들고, 하네스는 교육 도구의 허용 검사 작업을 실제 실행한다.
제품 검사 재실행·출시 승인과 혼동하지 않는다.

프로젝트 터미널의 필수 명령:
  npm run harness:check
  npm run harness:approve -- --reason "직접 검토한 범위와 이유"
  npm run harness:run
  npm run harness:drill -- timeout
  npm run harness:drill -- forbidden
  npm run harness:status
  npm run harness:resume -- --latest
승인 이유는 현재 파일을 직접 검토한 자기 말로 쓴다. 로컬 선언은 신원 인증·조직 승인이 아니다.
Copilot은 조직 승인 도구로 수동 사용하며 모델 API를 자동 호출하지 않는다.

필수 운영:
  실제 자식 프로세스 timeout의 실패·중단 기록을 보존한다.
  금지 도구는 프로세스 실행·보호 쓰기 전에 거절됐는지 확인한다.
  성공 후 허용 instructions를 수정해 stale 상태·옛 근거 resume 거절을 확인한다.
  사람이 현재 파일을 재검토·승인한 새 실행을 남긴다. 바뀐 fingerprint는 강제 재개하지 않는다.
  제공 절차의 동일 fingerprint 중단 작업을 checkpoint에서 재개하고 재시도 상한,
  성공 단계 재사용과 완료 작업 재개 시 중복 효과 부재를 확인한다.
차단 훈련·stale 거절의 실제 nonzero는 예상 상태다. 성공 exit로 꾸미거나 실패 기록을 지우지 않는다.
실제 명령·시각·exit·fingerprint·checkpoint/재시도·실행 여부·산출물 상대 경로는 기존 여섯 칸에 잇는다.
업무 v2 16개·개인 최소 4개·review 16개·독립 1개와 하네스 결과를 합산하지 않는다.

시간 교체:
  맥락 30분 = instructions/자료 10 + 주장 대조 15 + 상태/이유 5.
  계획 40분 = 입력/도구 경계 15 + 순서/checkpoint/중단 15 + 인수/기록 10. 읽기·선택한 coreRecord JSON 또는 워크북 여섯 칸 한 곳의 계획 기록만 한다.
  구축/변경 70분 = 승인 10 + 구축 25 + 업무 정책 15 + 실행 15 + 기록 5.
  검증 30분 = 업무 보존 10 + timeout/forbidden 10 + review 첫 실패 10.
  복구 30분 = review 10 + stale/안전 재개 8 + 독립 과제 7 + 회귀 5.
  인계 35분 = 구축/운영 인계 10 + 기존 여섯 명령 15 + 근거 해석/조건부 비교 10.
13:45 요청은 승인이 아니다. 내용 도움은 16:45 이후이면서 첫 예측·이유·테스트와 첫 실제 결과를
모두 동결한 뒤에만 연다. 미실행/차단은 unknown·exit null·HOLD로 보존하고 과정 지원만 받는다.
17:10–17:25 여섯 명령과 17:25 이후 조건부 공개는 그대로다.
교육 440분에 활동 265분 포함, 휴식 40분·점심 60분이다. HVE 수동 적용 40분은 요구사항 정제 필수이며
기존 실습 25분을 포함한다. 별도 과정·시간·양식은 없고 HVE 프레임워크는 사용하지 않는다.
하네스 구축·운영 근거가 없으면 기존 업무 검사가 통과해도 과정 완료는 HOLD다.
5항목 각 0–2점·합계 8점 이상·핵심 3항목 각각 1점 이상은 유지한다.
사람의 완료 시간은 미측정이며 기술 통과는 학습·현장 운영·조직 승인 인증이 아니다.

목표: 문제 → 문맥 → 계획/명세/가드레일 → 작은 변경 → 독립 검증 →
결함 복구/중단 → 내 실행 기록으로 재검증. 작성량이나 속도로 평가하지 않는다.
제공 골격은 failed만 검토 후보로 삼는 동작하는 v1 시작본이다.
완성이란 승인된 후보 범위 변경·review 복구·내 테스트/README와 세 하네스 파일 직접 구축·필수 운영 근거를 함께 갖춘 상태다.
빈 프로젝트나 핵심 함수 신규 작성은 아니다. demo에서는 승인된 buildId만 선택한다.
핵심 구현·데이터·출력 구조를 복제하지 않고 독립 기대값과 실제 요약을 비교한다.
AI가 낸 답과 통과 메시지는 근거를 대신하지 않는다. 최종 승인자는 사람인 나다.
작은 흐름은 결과 읽기 → 전체 검증 → 빌드 선택·중복 정리 → 상태·모듈별 요약 → 후보 보고다.
기존 demo는 operations/usage-cases.json 7건을 현재 소스로 실행한다.
operations/README.txt를 참고한다. 후보는 자문용이며 실제 검사 재실행이나 출시 승인이 아니다.
실제 UI·사용자 피드백·운영 노출은 검증하지 않았다. GREEN은 필요조건이지 운영 충분조건이 아니다.
현재 계약은 승인 이력으로, 코드 상태는 실제 소스/실행으로 확인한다. 오래된 대화는 권위가 아니다.

요구·계획·개발의 토대 — DDD와 BDD
--------------------------------
domain-behavior.txt를 contract.txt/공개 입력과 함께 읽는다. DDD(도메인 주도 설계)로
업무 용어·전체 키·불변 조건·요약/실제 재실행의 경계를 정하고, BDD(Behavior-Driven
Development, 행동 주도 개발)로 업무/개발/QA 관점의 질문 → 구체적인 Given/When/Then →
독립 단언 → 승인된 최소 변경 → 기존 node:test 실행 → 증거를 연결한다.
개인 실습의 관점 질문이지 실제 다자 회의 기록이 아니다. Cucumber 설치나 새 서비스는 없다.
요구에서는 용어·예시를 정하고, 계획에서는 규칙→예시→허용 파일/보존 계약→정확한 검사
제목·명령→예상 관찰→증거 경로를 연결한다. 개발에서는 승인 후 RED/GREEN으로 확인한다.
domain-behavior.txt 3~5절의 공개 예시·실제 검사 제목·명령 설명을 기존 여섯 칸에서 참조한다.
새 제출 양식이나 검사 수를 더하지 않는다. 독립 전이에는 기존 무지원/두 동결 경계를 유지한다.

기록 정책 — 한 곳에 누적, 중복 입력 없음
-------------------------------------
워크북의 여섯 핵심 필드 또는 work-record.json.coreRecord 중 하나를 주 기록으로 선택한다.
purpose(목적), expected(독립 기대값), changeReason(변경 이유), execution(실행),
unknown(미확인), nextAction(다음 행동)을 문제와 성공 기준 단계부터 자가 검증과 결과 정리 단계까지 같은 기록에 누적한다.
HVE도 이 여섯 범주를 재사용한다. 워크북 106필드와 기존 coreRecord 필드는 바꾸지 않는다.
README 5항목과 handoff는 주 기록의 필드/실제 증거 상대 경로를 짧게 참조하면 된다.
PLAN, issue/context, runs, defect, addedTests, AI/비용 등 기존 상세 필드는 선택 양식이다.
이하 상세 필드 이름은 주 기록 참조로 대체 가능하며 같은 내용을 다시 쓰지 않는다.
단, 사람 승인·독립 기대값·RED/GREEN·첫 편집 전 기준선·덮어쓰기 금지·본인 테스트·
review·evidence 확인·본인 6명령 재현은 기록 양식과 무관하게 모두 필수다.
null은 미확인/미실행이며 실제 근거 없이 채우지 않는다. trace/원시 로그를 업로드하지 않는다.
사람 증거는 마지막에 몰아 쓰지 않는다. checkpointReview는 문제와 성공 기준(목적·성공 기준),
맥락과 모델 선택(맥락·모델·토큰), 요구 변경과 구현(승인·RED/GREEN), 수정과 재검증(검증·원인·전이),
자가 검증과 결과 정리(본인 재현·인수인계)에 실제 관찰 시각과 주 기록/증거 위치를 연결하는 메타데이터다.
5차원 purposeAcceptance/contextModelTokens/coreProcess/verificationCauseRepair/
selfReplayHandoff의 미관찰 값은 null이다. 기본 점수/총점/완료 판정은 만들지 않는다.
독립 전이의 도움 상태와 실제 결과는 independentPractice 또는 주 기록 참조로 분리한다.
not-attempted / attempted-unassisted / hint-assisted / answer-assisted / incomplete는
도움·시도 상태이며 pass / fail / unknown은 실제 결과다. 통과만으로 독립 숙달을 확정하지 않는다.
실패/미실행 전이는 독립 역량 관찰을 unknown으로 남기고 unknown/nextAction에 후속 확인을 적는다.
7분 전이는 시간 설계이지 사람 학습자에게 관찰된 소요시간/학습 효과가 아니다.
제작·엔지니어링 검증 로그는 사람 학습/JS 능력/Copilot 사용·정책 준수의 증거가 아니다.


0. 실행 환경과 범위
------------------
VS Code에서 example-project/만 연다. 터미널의 작업 위치도 이 폴더로 한다.
instructor/는 학습자 작업 영역/AI 문맥/공개 저장소 배포본에서 제외한다. CR-01만 13:45에 공개하며
복구/전이 답안과 최종 참조는 본인 재현 뒤 17:25에 강사가 공개한다.
Node.js 22 이상과 npm이 필요하다. Windows/macOS/Linux에서 아래 npm 명령은 동일하다.
Node 설치/터미널 준비가 어려우면 강사의 로컬 환경 지원을 받는다.
명령 실행은 로컬 npm 스크립트만 사용한다. npm install, 서버, 네트워크가 필요 없다.
브라우저 UI, DB, 실제 고객 자료, 자격 증명, 배포, 자동 업로드는 범위 밖이다.
Copilot CLI, MCP, 멀티에이전트, 관리자 권한, 클라우드는 필수 조건이 아니다.
VS Code Copilot 사용 가능 여부/조직 정책은 직접 확인한다. preflight는 로그인 검사가 아니다.
AI 상태는 used / unavailable-policy(N/A) / unavailable-outage로 구분한다.
미확인은 not-recorded로 남긴다. N/A는 AI 역량을 완료했다는 뜻이 아니다.
사용 불가 시 같은 계약·수동 검토·실행 증거로 진행하며 강제 AI/정책 우회는 없다.

교육 전 준비 — 수업 전만, 실제 수업 사본과 분리:
공개 저장소 https://github.com/ijhan-biz/lgvs-copilot-intermediate-workshop 의 새 clone이나
GitHub Code → Download ZIP 소스 사본을 별도 연습 폴더에서 쓴다. 소스 ZIP은 모두 압축 해제한다.
제작 원본 폴더와 공개 저장소는 별개다. 이 폴더 전체나 기존 개인 기록을 배포/복사하지 않는다.
그 연습 사본에서 npm run preflight로 환경을 확인한다. preflight는 파일을 생성/수정하지 않는다.
readiness/task.txt에 따라 readiness:check의 최초 실패→한 상수 편집→저장→재실행을 확인한다.
교육 시작에는 새 clone 또는 새 GitHub 소스 압축을 새 수업 폴더에 준비한다.
별도 제작 ZIP/PDF는 필요 없다. 연습 결과/기준선/개인 기록을 수업 사본에 복사하지 않는다.
readiness는 교육 전 편집·저장·실행 관찰용이며 수업 활동이나 자가 검증과 결과 정리 추가 명령이 아니다.
준비·지원 증거는 승인된 합성 예제·별칭·명령/exit·최소 가림 출력·참조만 공유한다.
개인·회사 프롬프트/대화 전문, 전체 디버그 로그, 신원·계정 화면은 제출하지 않는다.
재현에 필요한 입력 조건·버전·단언 위치는 남기되 프록시·로그 수집기를 추가하지 않는다.

수업 시작 확인:
  npm test
  npm run test:v1
  npm run demo
기대: v1 각각 16/16 통과. 교육 전 preflight exit 0은 환경 확인일 뿐이다.
공개 입력 8행 중 BUILD-DEMO-1은 원본 7행·고유 6개·중복 1행이다.
상태별 건수는 passed 2 / failed 2 / timed_out 1 / not_run 1이다.
다른 빌드 1행은 위 건수에 더하지 않는다. v1 후보는 failed 2개다.
이 입력 상태 건수와 node:test가 실행한 테스트 통과 수는 서로 다른 값이다.
실패하면 새 기능을 만들지 말고 위치/Node 버전/오류를 기록하고 지원을 요청한다.

결과 화면 (선택 · 읽기 전용):
  npm run web
브라우저로 http://127.0.0.1:4173 을 연다. src를 고친 뒤 ↻ 결과 새로고침을 누르면 지금 코드로 다시 계산한다.
입력 8행→후보 흐름, 지금 코드의 후보 정책, 내 진행 상태(기준선·검사·하네스·기록)를 그림으로 보여 준다.

평가 기록
---------
자가 잠정 평가는 17:25–17:35 기존 비교·기록 10분 안에서 한다. 17:35–17:50 강사 해설과 구분한다.
그 뒤 강사가 실제 사람 증거로 5개 차원을 각각 0~2점으로 확인한다:
purposeAcceptance 목적·성공 기준 / contextModelTokens 맥락·모델·토큰 /
coreProcess 핵심 작업 과정 / verificationCauseRepair 검증·원인 수정 /
selfReplayHandoff 본인 재현·인수인계.
0=실제 수행을 확인했으나 기준 미달, 1=부분 근거/설명 보완 필요, 2=근거 연결과 본인 설명/재현 확인.
미실행·미확인·근거 미열람은 0으로 짐작하지 않고 점수/총점/완료 판정을 보류한다.
합계 8/10 이상이고 필수 3개(① 핵심 작업 과정 ② 검증·원인 수정
③ 본인 재현·인수인계)가 각각 1점 이상이어야 완료다. 안전한 중단만으로 자동 완료하지 않는다.
자동 채점은 없다. 확인 전 점수/총점/최종 판정은 null로 둔다.
AI 불가도 같은 결과·수동 검토로 5차원을 평가한다. 자동 탈락/점수 부여는 없다.
AI 역량은 미관찰로 따로 남겨 강사가 추후 허용 환경에서 확인한다. N/A로 AI 점수를
완료 처리하지 않는다. reviewerStatus의 대기/표본확인/보완/최종확정을 자가 판정과 구분한다.
