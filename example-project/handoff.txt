내 실행 안내 — 다음 사람이 이 파일만 보고 이어받는 곳
=====================================================
기록은 프로젝트 안에만 남긴다. 따로 적는 기록장이나 양식은 없다.
  기대값      → test/learner.test.mjs, test/transfer.test.mjs (실행 전에 먼저 쓴다)
  하네스 승인 → npm run harness:approve -- --reason "직접 검토한 범위와 이유"가 .harness에 남긴다
  실행 결과   → 명령 출력, evidence/v2-*.json, npm run harness:status
  목적·변경 이유·실제 결과·제한 → README.txt 맨 끝 [학습자 완성란]
  계획·원인 가설·받은 도움·미확인·다음 행동 → 아래 칸
빈칸은 미실행/미확인이다. 하지 않은 것을 채우지 않고, 옛 GREEN을 새 실행으로 쓰지 않는다.
짧게 써도 조건·예외·미확인은 남긴다.
이 파일과 README.txt는 하네스 fingerprint 대상이다. 6장 2번 도장부터 7장 이어 하기 확인까지는 열어 보기만 하고,
8장 마지막 하네스 실행 뒤에는 고치지 않는다. 고치면 승인과 재개가 거절된다.

재현 전제
  Node 22 이상, example-project 폴더 안에서 친다. 명령의 뜻과 예상 출력은 domain-behavior.txt 5절.
  승인된 C2-v2(후보 failed·timed_out·not_run)와 그대로 둔 C1·C3~C6.
  호출은 summarizeTestResults(results, { buildId }). src/·review/·data/test-results.json을 구분한다.

본인 6명령 — 새 터미널에서 이 문서만 보고 다시 친다
  npm run preflight
  npm run test:v2
  npm run test:learner
  npm run test:review
  npm run demo
  npm run evidence
기대: test:v2 16 · test:learner 4 · test:review 16 통과, 모두 종료 0. 실제 수와 종료 숫자는 직접 확인한다.
  BUILD-DEMO-1: 원본 7 · 고유 6 · 중복 1, passed 2 · failed 2 · timed_out 1 · not_run 1 (다른 빌드 1행은 세지 않는다)
  후보: v1 2개 → 승인된 v2 4개, 처음 나온 순서 그대로. 후보는 권고일 뿐 재실행·출시 승인이 아니다.
  learner 4 = 제공 1 + 똑같은 반복 1 + 승인 후 후보 확장 1 + C6 원본 보존 1.
  test:transfer(혼자 풀기 1개)는 여섯 명령에 넣지 않는다.

evidence/v2-*.json — 여섯 명령 뒤에 생긴다
  passed는 status passed, tests = passed = 16, 나머지 0, testExitCode·collectorExitCode 0, 전후 해시 동일일 때만.
  서명된 증명이 아니며 learner·review·승인·AI 사용까지 증명하지 않는다.
  환경변수·비밀·계정·개인 경로·원시 로그를 넣거나 올리지 않는다.

지킬 것
  baseline은 첫 편집 전에 딱 한 번, prepare:review도 딱 한 번. .baseline·review는 지우거나 덮어쓰지 않는다.
  업무 변경은 CR-01 요청을 사람이 승인한 뒤에만 한다. 승인 범위와 이유는 README 변경이유 줄에 적는다.
  새 검사는 RED를 먼저 보고 GREEN으로 만든다. 검사·계약·공통 16개를 약하게 하거나 지우지 않는다.
  여러 실패를 여러 결함으로 단정하지 않는다.
  혼자 풀기는 예측·이유·expectedIds를 먼저 쓰고 사본을 둔 뒤 한 번 실행한다. 그동안 AI·힌트·도움은 닫는다.
  도움 뒤 통과는 혼자 통과가 아니다. 확인한 fail은 그대로 두고, 실행하지 못했으면 unknown으로 남긴다.

마지막 순서
  1. 지금까지 실제로 본 결과로 README [학습자 완성란]과 위 칸을 채우고 저장한다.
  2. 새 채팅(없으면 손)으로 비판받고 채택/기각을 [받은 도움]에 적는다.
  3. 현재 파일을 다시 읽고 도장 → 실행 → 상태. 결과는 .harness에 남으니 옮겨 적지 않는다.
     npm run harness:approve -- --reason "직접 검토한 현재 파일의 범위와 이유"
     npm run harness:run
     npm run harness:status
  4. 새 터미널에서 여섯 명령. 이 뒤로 README·handoff는 고치지 않는다.
     재현 결과가 적은 내용과 다르면 강사에게 알리고, 고쳐 적었다면 3부터 다시 한다.
  5. 혼자 풀기와 여섯 명령을 마친 사람만 참고답안과 비교한다. 비교 메모는 README·handoff 밖에 쓴다.

평가는 강사가 테스트·승인 기록·evidence·README·handoff를 직접 보고 한다. 자가 채점은 없다.
  다섯 가지 각 0–2점: 목적·성공 기준 / 맥락·모델 판단 / 핵심 작업 과정 / 검증·원인 수정 / 본인 재현·인수인계.
  합계 8/10 이상, 마지막 세 가지는 각 1점 이상. 확인하지 못한 것은 점수로 짐작하지 않는다.
