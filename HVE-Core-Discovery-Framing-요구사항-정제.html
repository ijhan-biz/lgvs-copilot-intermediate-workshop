요구사항 정제

“무엇을 만들어 달라”는 요청을 곧바로 코드로 옮기지 않고, 누가 어떤 판단을 해야 하는지부터 확인하는 과정입니다.

공식 방법과 수업용 가상의 구분

방법 설명은 microsoft/hve-core의 고정 버전을 따릅니다. 아래 역할 대화·관찰·주제·문제·요구사항은 모두 합성 교육 예시입니다. 실제 인터뷰, 고객 합의, 도구 실행 결과가 아닙니다. 로컬 계약과 공개 합성 데이터로 확인되는 것은 실습 규칙뿐이며, 실제 고객의 필요를 입증하지 않습니다.

권장 진행은 핵심 도식·사례 설명과 10분 짝 실습을 포함한 60분입니다. 세부 태스크와 보충 예시는 자율 학습에서 이어 읽습니다. 마지막에는 요청에서 달라진 내용, 근거와 가정의 차이, 다음 확인 담당자를 설명하고 요구사항 검토 초안을 작성합니다.

도입 · 5분

전체 흐름

“서류를 정리하고 처리까지 해 주세요”라는 부탁을 받았다고 생각해 봅시다. 먼저 어떤 서류인지, 누가 검토할지, 누가 처리할 권한을 가졌는지 알아야 합니다. 날짜별로 잘 묶었다고 해서 결재까지 대신할 수는 없습니다. 테스트 결과도 같습니다. 정리할 기준을 찾는 일과 실제로 재실행을 허가하는 일은 다릅니다.

프로세스는 모호한 부탁에서 근거 있는 다음 결정까지 가는 전체 일의 흐름입니다. 그 안에서 조사처럼 한 종류의 불확실성을 줄이는 구간이 단계입니다. “QA에게 최근 결과 검토를 보여 달라고 묻기”는 그 단계에서 사람이 수행하는 하나의 태스크입니다. 태스크를 했다는 사실보다 “추측과 실제 작업을 구분할 근거가 생겼는가”라는 목표가 중요합니다. “선호를 묻기 전에 현재 작업을 본다”는 원리입니다. 아직 보지 않은 일을 원하는 답으로 채우는 오류를 막기 위한 이유입니다.

Discovery & Framing은 이 강의에서 Design Thinking의 문제 공간(Problem Space)을 묶어 부르는 교육용 이름입니다. 공식적인 네 번째 RPI 단계나 실행 명령이 아닙니다. 더 넓은 개발 생애주기의 Discovery, Design Thinking의 사용자 조사, RPI Research의 후속 조사는 서로 같은 단계가 아닙니다.

넓은 의미의 Discovery는 투자할 가치가 있는 문제와 기회를 알아보는 활동 전반입니다. DT 문제 공간은 그중 사용자·상황·문제를 이해하는 데 집중합니다. 팀이 이후 RPI Research를 선택하면, 정리된 문제를 받아 기존 코드·기술 제약·구현 가능성처럼 엔지니어링의 질문을 조사할 수 있습니다. 같은 사용자 인터뷰를 이름만 바꿔 반복하는 뜻도, 모든 팀이 반드시 그 경로를 거쳐야 한다는 뜻도 아닙니다.

정제 전 · 합성 요청

“테스트 결과를 자동으로 정리하고 재실행까지 해줘.”

누가 볼지, 무엇을 같은 검사로 셀지, 어떤 상태를 포함할지, 누가 실행을 허가할지 빠져 있습니다.

정제 후 · 합성 초안

“QA가 선택 빌드의 상태와 실패 후보의 근거를 확인하도록 돕는다. 후보 제공과 실행 허가는 구분한다.”

수단이 아니라 사용자의 판단을 먼저 다룹니다. 실제 필요와 권한은 아직 검증 대상입니다.

DT Coach의 역할과 시작점

DT Coach는 질문하고 관찰을 짚으며 다음 선택을 돕는 코치입니다. 고객이 승인한 요구사항을 자동으로 확정하는 에이전트가 아닙니다.

  1. VS Code에서 GitHub Copilot Chat을 엽니다.
  2. 상단 에이전트 선택기에서 DT Coach를 선택합니다.
  3. 자연어로 상황과 확인하고 싶은 문제를 설명합니다.

이 강의는 실제 설치·확장·조직 정책의 사용 가능 여부를 확인하지 않았습니다. 선택기에 없다면 설치 명령을 추측하지 말고, 아래 준비된 대화와 수동 작성 항목으로 시연합니다. 실제 에이전트 호출로 기록하지 않습니다. 여기서는 대상 저장소를 조작하거나 코드·테스트를 만들지 않습니다.

강사 노트 · 설명의 도착점

“요구사항 문장이 길어졌다”가 아니라 “무엇이 확인됐고 무엇은 아직 모르는가”를 설명하게 합니다. 오늘은 수업용 초안을 끝내지만 실제 고객 조사나 문제 공간의 공식 종료를 완료하지 않습니다. 모든 프롬프트는 강의 작성자가 만든 예이며 공식 내장 프롬프트가 아니고 실행한 기록도 아닙니다.

Scope Conversations · 10분

범위와 이해관계자

지금 가진 컨텍스트
최초 요청과 공개 실습 계약은 있지만, 누가 어떤 판단에 쓸지는 모릅니다. 컨텍스트는 문장의 뜻을 판단하는 데 필요한 배경과 경계입니다. AI에 파일이나 토큰을 많이 넣는 것만을 뜻하지 않습니다.
이번 단계의 목표
재실행 기능을 고르기 전에 사용자·결정·확인할 사람을 찾아 조사 질문을 정합니다.
이 순서를 지키는 원리
부탁한 사람, 실제 사용자, 승인권자는 서로 다를 수 있습니다. 먼저 구분하지 않으면 요청자의 아이디어를 사용자의 필요나 승인으로 오해합니다.

공식 세부 흐름은 범위 계획(1a) → 대화 실행(1b) → 범위 기록(1c)입니다. 먼저 물을 것은 “어떤 화면이 필요한가”가 아니라 “이 결과를 보고 누가 무슨 결정을 하는가”입니다.

같은 요청도 사용자가 QA인지 운영자인지에 따라 필요한 결과가 달라집니다. 시작 상황이 일일 검토인지 장애 대응인지 모르면 언제 쓰는지 알 수 없습니다. 데이터의 빌드 경계가 없으면 다른 빌드까지 합칠 수 있고, 규칙이 없으면 시간 초과도 실패로 셀 수 있습니다. 권한이 없으면 후보를 보여 달라는 요청을 실행 허가로 잘못 읽을 수 있습니다. 빠진 배경은 추정으로 메우지 않고 질문으로 남깁니다.

계획에서 거친 기록까지

  1. 조사 담당자가 대화를 계획합니다. 최초 요청을 원문 그대로 남기고 “누가 이 결과를 보나요?”를 먼저 묻습니다. 사용자·인접 역할·책임자 후보를 적어 다음 대화에 누구를 초대할지 정합니다. 이것이 이해관계자 지도입니다.
  2. 역할별로 결정을 묻습니다. QA에게는 마지막 검토와 후속 전달을, 개발자에게는 같은 검사의 기준을, 책임자에게는 권한의 근거를 묻습니다. 각 답이 다음 질문의 범위를 좁힙니다. 대답하지 못한 질문도 기록합니다.
  3. 조사 담당자가 대화 내용을 거칠게 기록합니다. 포함·제외 범위와 전제를 짧은 글머리표나 표로 남깁니다. 예쁜 도식이나 완성 문서가 있어야 끝나는 단계가 아닙니다. 다음 조사자가 무엇을 관찰할지 알면 됩니다.
합성 교육 예시 · 이해관계자와 확인할 결정
역할관심과 질문확인 책임
QA어떤 빌드에서 무엇을 다시 검토해야 하는가? 현재 어떤 자료를 대조하는가?후보를 찾는 실제 작업과 누락·오판 상황을 설명합니다.
개발자같은 검사의 기준은 무엇인가? 반복과 충돌은 어떻게 구분하는가?데이터 의미와 기술 제약을 확인합니다. 실행 권한을 대신 승인하지 않습니다.
릴리스 판단 책임자검토 후보를 실행해도 되는 조건은 무엇인가? 출시 판단은 누가 하는가?실제 권한과 의사결정 절차를 확인해야 합니다. 이 예시에서는 검증되지 않았습니다.

보안·운영 담당자 등이 더 필요한지는 실제 환경에서 확인합니다. 이 강의가 LGVS의 실제 보안 정책이나 승인 체계를 알고 있다고 가정하지 않습니다.

합성 역할 대화 · 실제 인터뷰 아님

QA: “결과를 정리한 뒤 다시 볼 검사를 찾고 싶어요. 지금은 빌드별 행을 골라 같은 기록인지 대조한다고 가정해 볼게요.”

개발자: “검사 번호가 같아도 모듈이 다르면 다른 검사예요. 이 규칙은 실습 계약에서 확인할 수 있어요.”

릴리스 판단 책임자 역할: “후보를 보았다는 사실만으로 실행하거나 출시해도 된다는 뜻은 아니에요.”

합성 현재 흐름: QA가 빌드 선택 → 결과 행 대조 → 상태 집계 → 검토 후보 전달을 수동으로 한다고 가정합니다. “실제로 이렇게 일한다”는 사실이 아니라 다음 조사에서 관찰할 가설입니다. 사용자가 내려야 할 결정은 어떤 검사를 어떤 근거로 후속 검토에 올릴지이며, 실제 실행·출시 결정은 별도입니다.

고정 조건과 협의 조건

공식 자료의 Frozen/Fluid는 처음 요청의 형태와 제약의 변경 가능성을 따로 분류합니다. 요청에서는 Frozen이 “챗봇을 만들어 달라” 같은 구체적인 해결책 요청, Fluid가 “AI를 활용하고 싶다” 같은 막연한 바람입니다. 구체적인 요청도 그 배경 문제를 더 물어야 합니다. “자동 재실행”이 구체적인 요청이라는 사실은 변경할 수 없는 요구이거나 승인된 기능이라는 뜻이 아닙니다.

제약에서는 별도로 고정 조건과 협의 가능한 조건을 나눕니다. 아래 실습 계약은 이번 수업에서 지킬 고정 조건이지만, 최초 요청의 분류나 실제 고객 필요의 검증 상태와는 다릅니다.

합성 범위 기록 · 출처와 변경 책임의 분리
구분내용과 출처담당 / 다음 확인
고정 · 실습 안에서 확인처음에는 실패만 후보로 둡니다. 같은 검사는 빌드·모듈·검사 식별자로 구분합니다. 출처는 공개 계약입니다.수업 계약의 변경 권한을 가진 사람만 변경할 수 있습니다. 실제 고객 정책으로 일반화하지 않습니다.
포함 · 수업 검토 범위선택 빌드의 요약과 후보 근거를 읽는 일을 다룹니다. 출처는 실습 목적과 합성 문제 가설입니다.QA 역할이 필요를 설명하고 실제 사용자 확인은 후속 조사로 남깁니다.
제외 · 실습 경계실제 검사 실행, CI 제어, 출시 승인, 운영 데이터 수집, 코드·테스트 변경은 다루지 않습니다.강의 진행자가 경계를 지킵니다. 실제 업무의 권한 책임자는 별도 확인합니다.
협의 가능 · 가정QA가 요약을 보고 검토 후보를 전달한다는 흐름과 표시 방식은 합성 대화에서 제안한 가정입니다.QA·개발자가 작업을 보여 주고 릴리스 판단 책임자가 후속 절차를 검증해야 합니다.

AI 전제 목록

실습 규칙으로 확인
후보 제공은 실제 실행이 아닙니다. 처음 후보는 실패만 포함합니다. 계약으로 확인했지만 고객 필요의 근거는 아닙니다.
검증 전 가정
사람이 후보와 원본 근거를 함께 보면 판단에 도움이 될 것이라는 합성 필요 가설입니다.
미확인
실제 실행 승인자, 현행 작업 시간, 필요한 처리량, 허용 응답 시간, 조직 정책은 모릅니다.
의견 충돌

작업을 따라가는 조사 태스크

  1. 조사 담당자가 계획합니다. QA에게 볼 작업과 공유 가능한 기록 범위를 확인하고, 개발자와 권한 책임자에게 확인할 질문을 나눕니다. 이 계획이 관찰 순서의 출발점입니다.
  2. QA에게 환경을 보여 달라고 묻습니다. “결과는 어디에 있고 빌드는 어떻게 고르나요?”라고 묻고 사용 자료와 시작 상황을 기록합니다. 이 배경이 있어야 다음 행동의 뜻을 읽을 수 있습니다.
  3. 최근 작업을 순서대로 따라갑니다. “다음에는 무엇을 비교했나요?”라고 묻고 빌드 선택·행 대조·후보 전달을 관찰합니다. 설명과 실제 행동이 다르면 둘 다 남기고 이유를 묻습니다.
  4. 개발자와 책임자에게 제약을 검증합니다. “같은 검사라는 기준은 무엇인가요? 실행 허가의 근거는 어디에 있나요?”를 묻습니다. 계약으로 확인한 수업 규칙과 아직 못 만난 실제 책임자의 권한을 섞지 않습니다.
  5. QA에게 남은 어려움과 반대 사례를 묻습니다. “지금 방식으로 충분한 경우는 언제인가요? 조건을 먼저 봐야 하는 경우는요?”를 물어 자동 재실행이 아닌 다른 필요도 열어 둡니다.
  6. 조사 담당자가 원문을 충실히 남깁니다. 발언·관찰에 상황, 출처, 실제 확인 여부를 붙이고 자신의 해석은 분리합니다. 다음 종합 단계가 이 기록으로 돌아와 판단하게 합니다. 여기서 견고한 주제를 미리 확정하지 않습니다.

합성 조사 계획

아래는 실제 조사 전에 검토할 교육용 계획 예시입니다. 실제 참여자 모집이나 인터뷰는 수행하지 않았습니다.

  1. 대상: 직접 사용자 QA, 인접 역할 개발자, 의사결정 역할 릴리스 판단 책임자입니다. 필요하면 환경을 아는 운영·보안 담당자를 추가합니다.
  2. 순서: 환경 확인 → 작업 흐름 질문 → 제약 검증 → 충족되지 않은 필요 탐색으로 진행합니다.
  3. 방법: 공개 합성 자료로 빌드 선택과 후보 판단을 보여 달라고 요청하고, 짧은 역할 인터뷰와 작업 관찰을 함께 설계합니다.
  4. 기록: 발언 원문, 보인 행동, 자료 출처, 상황, 연구자의 해석을 별도 칸에 남깁니다. 실제 조사에서는 공유 동의와 기록 범위를 먼저 확인합니다.
  5. 중단·보완: 출처가 없거나 관찰과 설명이 어긋나면 결론을 쓰지 않습니다. 권한 책임자를 만나지 못하면 그 부분은 미확인으로 남깁니다. 수업 시간 종료는 실제 조사의 충분성을 뜻하지 않습니다.

실제 종합에서는 복수의 독립적인 출처로 각 주제를 지지해야 합니다. 아래는 묶는 방법을 보여 주는 합성 주제 초안이며 실제로 검증된 패턴이 아닙니다.

임시 주제연결한 합성 자료의미와 남은 질문
후보의 식별 근거“QA의 후보 확인 발언” + “개발자의 식별 설명”이름만 같다고 같은 검사로 볼 수 없습니다. 실제 사용자가 어떤 근거로 대조하는지 관찰해야 합니다.
건수와 원본의 신뢰“중복 대조 관찰 역할극” + “QA의 후보 확인 발언”반복을 중복 집계하지 않고 원본 근거를 확인할 필요가 있을 수 있습니다. 현행 오류나 빈도는 모릅니다.
후보와 실행의 경계“QA의 권한 발언” + “개발자의 권한 발언” + “QA의 반대 사례”후보 제공이 실행 허가가 되면 안 됩니다. 권한 충돌은 실제 릴리스 판단 책임자에게 돌려보냅니다.

버릴 요약 · 합성 예시

최초 해결책을 반복하고, 반대 사례와 권한 충돌을 지웠습니다. 근거가 지지하지 않습니다.

남길 통찰 · 합성 가설

“실행을 자동화하기 전에, 믿고 검토할 후보와 그 근거가 필요할 수 있다.”

식별·중복·권한의 차이를 보존합니다. 실제 필요로 확정하지 않고 조사 대상으로 남깁니다.

문제 정의 · 합성 교육 초안

QA는 빌드 결과를 검토할 때, 같은 검사의 범위와 반복 기록을 일관되게 구분할 근거가 부족하면 어떤 항목을 후속 검토에 올릴지 판단하기 어렵습니다. 상태별 현황과 원본 근거를 확인해 검토 후보를 신뢰할 수 있어야 하며, 실행 권한은 별도로 확인해야 합니다.

사용자(QA)·상황(빌드 결과 검토)·장애(식별과 반복 구분의 어려움)·영향(후속 검토 판단의 어려움)·필요 결과(근거 있는 후보 판단)를 담았습니다. 챗봇·대시보드 같은 해결책은 지정하지 않았습니다.

탐색 질문 · 합성 교육 초안

어떻게 하면 QA가 선택한 빌드에서 후속 검토가 필요한 검사를 근거와 함께 판단하면서, 검토 후보와 실제 실행 허가를 혼동하지 않게 도울 수 있을까요?

문장 수정의 예: “모두 자동 재실행을 원한다”에서 “근거를 확인하며 검토 후보를 판단할 필요가 있을 수 있다”로 바뀌었습니다. 식별 관련 발언을 연결하면서도 자동 실행의 반례를 보존했기 때문입니다. 바뀐 문장이 그럴듯하더라도 독립 근거가 없으면 가설 상태를 유지합니다.

요구사항과 인수 기준

문제 정의 다음에 곧바로 구현을 승인하는 것은 아닙니다. 이 수업에서는 이미 주어진 요약 함수를 검토한다는 실습 제약을 적용해, 합성 문제 가설이 어떤 관찰 가능한 행동 초안으로 이어지는지 봅니다. 이 함수가 Method 3에서 반드시 발견되는 정답은 아닙니다.

구체적인 예를 먼저 쓰는 원리
“같은 검사”나 “후보”의 뜻이 다르면 같은 문장으로도 다른 기능을 만듭니다. 용어와 예시부터 대조하면 코드 없이도 오해를 찾을 수 있습니다.

업무의 말에서 검토 가능한 행동까지

  1. 업무 담당·개발·QA 역할이 질문을 찾습니다. “번호가 같아도 모듈이 다르면 하나인가요? 후보면 바로 실행해도 되나요?”처럼 뜻이 갈리는 질문을 적습니다.
  2. 개발과 QA 역할이 수업 계약을 대조합니다. 같은 검사의 세 부분, 반복과 충돌, 실패만 후보라는 처음 규칙을 확인합니다. 이는 수업 규칙 확인이며 실제 업무 담당자의 합의가 아닙니다.
  3. 세 관점에서 구체적 예를 논의할 준비를 합니다. 공개 8행을 손으로 분류해 기대 건수와 후보를 구합니다. 실제 업무에서는 이 예를 업무 담당·개발·QA가 함께 논의해 의미를 맞춥니다. 여기서는 그 논의를 제안하는 데 그칩니다.
  4. QA 역할이 관찰 기준을 초안에 연결합니다. 하나의 요청 행동 앞뒤에서 볼 결과와 오류를 적습니다. 뒤의 개발 단계가 합의된 예를 기존 검사와 연결할 수 있게 하되, 지금 실행하거나 승인하지 않습니다.

  3. 근거 · 합성 역할극“식별 근거가 필요하다는 발언과 자동 실행의 반대 사례가 있다.”
    추가된 정보: 이름만으로 구분할 수 없고 권한 의견도 충돌합니다. 실제 근거는 아직 없습니다.
  4. 문제 · 합성 가설“원본 근거를 확인하며 신뢰할 검토 후보를 판단해야 한다.”
    변경된 점: 자동 실행이라는 수단에서 판단이라는 필요한 결과로 옮겼습니다.
  5. 요구사항 · 수업용 검토 초안“주어진 함수로 선택 빌드의 상태와 처음 정책의 후보를 반환한다.”
    추가된 정보: 공개 계약이 대상 함수와 행동의 경계를 정합니다. 고객 승인으로 바뀐 것은 아닙니다.
  6. 관찰 기준 · 계약 기반 합성 예시“공개 8행에서 선택 빌드의 원본 7·고유 6·중복 1과 후보 2개를 확인한다.”

자동 검사 실행·릴리스 승인·CI 제어·화면 설계·후보 정책 확대입니다. 이 강의에서는 구현·테스트도 작성하지 않습니다.
오류 행동
모든 빌드의 행과 옵션을 검증한 뒤 대상 빌드를 집계합니다. 잘못된 입력과 충돌은 TypeError로 알립니다. 다른 빌드의 오류도 무시하지 않습니다. 정상 빈 입력이나 일치 빌드 없음만 전체 0건과 새 빈 배열입니다.
원본과 반환값
입력 배열·행·옵션은 바꾸지 않습니다. 요약·건수·모듈·후보 컨테이너는 새로 만들고 후보 항목은 처음 남긴 원본 행을 가리킵니다.
성공 확인
아래 계약 기반 행동 예시의 정확한 건수·후보·오류·순서·참조를 만족하는지 후속 단계에서 확인합니다. 업무 효과는 후보와 근거 식별의 시간·정확도로 측정하도록 계획하되, 성능 목표는 기준선 확인 후 결정합니다.
가정과 미확인
요약이 QA의 판단에 도움이 된다는 필요는 합성 가설입니다. 실제 작업 흐름·실행 권한·성능 목표는 미확인입니다. 상충한 권한 발언은 해결되지 않았습니다.
담당과 승인 상태
수업에서는 QA 역할이 초안을 검토하고 개발자 역할이 계약 대조를 맡습니다. 실제 업무 필요는 사용자, 실행 권한은 해당 책임자의 확인이 필요합니다. 실제 담당자 지정·고객 승인·구현 허가는 없습니다.

DDD와 BDD의 연결

DDD(도메인 주도 설계)는 업무의 말과 규칙을 함께 이해하는 관점입니다. 여기서는 “같은 검사”, “중복”, “후보”가 무엇인지 일치시킵니다. 새 클래스 구조를 만들라는 뜻이 아니며, DDD 문서가 HVE DT의 필수 산출물이라는 뜻도 아닙니다.

예를 들어 검사 번호만 같아도 모듈이 다르면 다른 검사입니다. 빌드·모듈·검사 식별자 세 값이 하나의 검사 경계를 정합니다. 여기에 이름·상태까지 똑같은 행이 반복되면 새 검사가 추가된 것이 아닙니다. 후보라는 말도 “사람에게 검토를 제안할 항목”이지 “재실행을 허가한 항목”이 아닙니다. 같은 단어의 뜻과 책임 경계를 맞추는 일이 여기서의 DDD 적용입니다.

BDD(행동 주도 개발)는 업무 질문으로 행동을 발견 → 구체적 예시로 합의 → 나중에 자동화하는 흐름입니다. Given/When/Then 문법만 쓰는 일이 아닙니다. 여기서는 합의할 예시를 제안할 뿐 실제 관계자 합의를 했다고 기록하지 않습니다.

Given은 행동 전의 상황입니다. 위 예에서는 “같은 실패 기록 두 행이 주어졌다”입니다. When은 한 번의 행동으로, “그 빌드를 요약한다”입니다. Then은 밖에서 확인할 기대 결과로, “실패 검사 하나와 첫 원본 후보 하나를 반환한다”입니다. 세 문장을 이어 읽으면 무엇을 주고 무엇을 하면 무엇을 보아야 하는지가 드러납니다. 형식에 맞게 썼다는 사실만으로 고객과 합의한 것은 아닙니다.

  • 사용자 관점: 이 후보를 보고 어떤 결정을 하는가? 후보가 실행 허가처럼 보이지 않는가?
  • 개발 관점: 같은 검사의 식별 기준과 입력 보존은 무엇인가?
  • QA 관점: 반복·충돌·정상 빈 결과를 각각 구분하는가? 다른 빌드의 오류도 잡는가?

HVE의 requirements-author는 행동 인수 기준에 Given/When/Then을 지원합니다. 이는 문제 정의 뒤의 연결 도구이며 사용자 조사를 대체하거나 DT 종료를 판정하는 관문이 아닙니다. 새 패키지나 Cucumber는 필요하지 않습니다. 나중에 기존 node:test와 연결하며 이 강의에서는 실행·작성하지 않습니다.

공식 근거: 관찰 가능한 인수 기준과 Given/When/Then · 수업 관점: 도메인과 행동 검증 안내.

다섯 행동 예시

공개 계약·합성 입력에 기반한 교육 예시입니다. 실제 테스트 실행이나 고객 승인이 아닙니다. 기대값은 처음 실습 계약과 입력을 읽어 정하며 AI 출력이나 실행 결과에서 역으로 만들지 않습니다.

전체 건수와 처음 후보

Given · 전제 공개 합성 8행과 선택 빌드가 있습니다.

When · 행동 처음 정책으로 요약을 요청합니다.

Then · 관찰 선택 빌드의 원본 7·고유 6·중복 1, 통과 2·실패 2·시간 초과 1·미실행 1입니다. 후보는 ‘재생 목록 불러오기’ → ‘블루투스 연결’ 두 개입니다. 다른 빌드의 1행은 집계에 더하지 않습니다. 모듈은 미디어 → 연결 → 설정 순서입니다.

정확한 반복과 충돌의 구별

Given · 전제 전체 식별자·이름·실패 상태가 같은 두 행이 있습니다.

When · 행동 그 빌드를 요약합니다.

Then · 관찰 원본 2·고유 1·중복 1, 실패 1·다른 상태 0이며 후보 하나는 첫 원본 행과 같은 참조입니다.

별도 반례: 같은 전체 식별자에서 이름 또는 상태를 다르게 한 경우에는 반복이 아닙니다. 같은 요청은 TypeError여야 하며 마지막 행으로 덮어쓰지 않습니다.

다른 모듈의 같은 검사 번호

Given · 전제 같은 빌드에서 검사 번호가 같고 모듈은 다른 유효한 두 행이 있습니다.

When · 행동 그 빌드를 요약합니다.

Then · 관찰 원본 2·고유 2·중복 0으로 별개 검사 두 개를 셉니다. 모듈의 첫 등장 순서를 유지합니다.

선택 밖 빌드의 잘못된 행

Given · 전제 선택 밖 빌드에 잘못된 상태 또는 같은 전체 식별자의 이름·상태 충돌이 있습니다.

When · 행동 다른 빌드를 요약해 달라고 요청합니다.

Then · 관찰 필터 전에 모든 입력을 검증하므로 TypeError입니다. 선택 밖이라고 무시하거나 정상 0건으로 반환하지 않습니다.

정상 빈 결과

Given · 전제 빈 배열 또는 선택한 빌드와 일치하지 않는 유효한 행만 있습니다.

When · 행동 요약을 요청합니다.

Then · 관찰 원본·고유·중복과 네 상태 모두 0이며 모듈·후보는 새 빈 배열입니다. 반복 호출도 새 요약과 컨테이너를 반환합니다.

모든 예시의 유지 조건: 원본 배열·행·옵션을 변경하지 않고, 결과 컨테이너는 새로 만들며, 후보 항목은 첫 원본 행의 참조입니다. 값이 같은 복사 행과 원본 참조는 다릅니다.

나중의 기존 검사 연결: 전체·모듈 집계, 처음 후보 정책, 정확한 반복, 이름·상태 충돌, 빈 결과, 순서·원본 보존을 확인하는 기존 node:test의 단언과 대응시킵니다. 정확한 실행 표기는 기술 참고에만 남깁니다. 지금 새 테스트나 구현을 만들지 않습니다.

수정과 멈춤의 기준: “실패를 모아 다시 실행한다”는 문장은 후보의 뜻을 확인한 뒤 “실패만 검토 후보로 반환하며 실행은 하지 않는다”로 고칩니다. 계약에서 직접 구한 기대값으로 행동을 설명할 수 있으면 수업 초안을 검토할 준비가 된 것입니다. 용어·정책이 갈리면 예시 논의로, 사용자 필요가 불명확하면 Research로 돌아갑니다. 고객 승인이나 구현 착수 준비가 끝난 것은 아닙니다.

강사 노트 · 초안과 검증의 경계

10분 안에 초안의 목적·범위·미확인을 먼저 읽고 다섯 행동 예시를 빠르게 대조합니다. 자세한 반환 구조는 기술 참고로 돌립니다. “검사에서 통과한 수”와 “입력에 통과로 기록된 건수”가 다름을 짚습니다. 이후 후보 확대를 이 초안에 미리 반영하지 않습니다.

짝 실습 · 10분

시간 초과 요청의 정제

새 합성 요청: “시간초과 결과도 보기 좋게 알려줘.”

이 말은 시간 초과를 재실행 후보에 추가하라는 승인이 아닙니다. 같은 공개 도구와 처음 계약을 유지합니다. 자료·코드·테스트·실습 정책을 변경하지 않습니다.

  1. 2분 · 질문: 한 명이 요청자, 한 명이 조사자 역할로 확인 질문 세 개를 작성합니다.
  2. 2분 · 분리: 계약에서 확인한 사실 두 개와 아직 검증하지 않은 가정 두 개를 구분합니다.
  3. 3분 · 작성: 문제 정의 한 문장, Given/When/Then 하나, 해결되지 않은 질문 하나를 씁니다. 구두나 개인 메모로 충분하며 새 산출물 파일은 요구하지 않습니다.
  4. 2분 · 짝 검토: 서로의 문장에서 근거·경계·만든 숫자 유무를 확인합니다.
  5. 1분 · 보류 선언: 수업에서 작성한 결과와 실제로 추가 조사해야 할 내용을 각각 말합니다.

짝 검토 기준

  • 사실마다 공개 계약의 근거를 설명할 수 있는가? 합성 발언을 실제 조사로 쓰지 않았는가?
  • “보기 좋게”를 어떤 사용자 판단·상황의 문제로 바꿨는가?
  • 상태를 보여 주는 일과 후보 정책 변경을 구분했는가?
  • 자동 실행·승인·효과 수치를 만들어 넣지 않았는가?
  • 추가로 확인할 역할과 질문이 남아 있는가?
접은 참고답안 · 합성 교육 예시

질문: 누가 어느 순간 시간 초과를 보나요? 지금 자료에서 무엇을 구분하기 어려운가요? 이 정보를 본 뒤 어떤 결정을 하며 누가 확인해야 하나요?

계약 사실 두 개: 시간 초과는 별도의 상태이며 전체·모듈별 건수에 포함합니다. 처음 후보에는 실패만 포함합니다.

가정 두 개: QA가 검토 사용자일 것이라는 가정, 현재 시간 초과의 의미나 위치를 찾기 어렵다는 가정입니다. 실제 업무에서 확인되지 않았습니다.

문제 정의 가설: QA가 빌드 결과를 검토할 때 시간 초과를 다른 상태와 구분하지 못한다면 후속 확인 항목을 판단하기 어려우므로, 상태의 의미와 해당 건수를 확인할 수 있어야 합니다.

행동 예시: 공개 합성 8행과 선택 빌드가 주어졌을 때(Given), 처음 정책의 요약을 요청하면(When), 시간 초과 건수는 1이며 실패 후보는 기존 두 개 그대로입니다(Then). 표시 방식이나 정책 확대는 이 예시에서 확정하지 않습니다.

미해결 질문: 시간 초과 정보를 확인한 뒤 누가 어떤 후속 검토를 승인하나요? 실제 책임자에게 질문합니다.

이 답은 실제 사용자 조사·정답 인증·독립 전이 과제의 해설이 아닙니다. 다른 문제 정의도 근거와 경계를 지키면 검토할 수 있습니다.

강사 노트 · 관찰할 말과 행동

“시간 초과도 후보에 넣자”가 나오면 “어느 문장이 그 변경을 승인했나요?”라고 묻습니다. 역할극을 잘 마쳤다는 사실과 실제 문제 공간 종료는 별개입니다. 학습 숙달이나 현장 효과를 검증했다고 보고하지 않습니다.

정리 · 5분

보류와 인계

Method 3 뒤에는 팀이 다음 경로를 고릅니다. Method 4 Brainstorming으로 전진하거나, Methods 1–2로 돌아가 보완하거나, 문제 공간의 측면 인계를 선택할 수 있습니다. 시간표가 대신 선택하지 않습니다.

지금까지 가져온 것
원래 요청, 수정한 문제 가설, 원문과 해석의 연결, 계약의 경계, 초안과 미해결 질문을 함께 가져옵니다.
이번 정리의 목표
다음 사람이 왜 이런 문제를 다루는지 이해하고, 무엇을 먼저 확인해야 하는지 선택할 수 있게 합니다. 파일 하나를 넘기는 일이 아니라 판단의 이유를 전달하는 일입니다.
보류를 허용하는 원리
인계 형식을 채워도 실제 근거와 권한이 생기지 않습니다. 코치는 서로 다른 말을 비교할 수 있지만 조직의 권한을 부여하거나 어느 발언이 승인인지 판정할 수 없습니다.

사람별 확인과 인계 태스크

  1. 조사 담당자가 근거를 묶습니다. 원래 요청과 새 문제 문장을 함께 두고, 각 주장에서 어떤 원문으로 돌아가는지 확인합니다. 합성·가정·미확인·충돌 표시를 수신자에게도 보이게 합니다.
  2. QA·개발자·권한 책임자가 각자 확인합니다. QA는 실제 작업과 필요를, 개발자는 데이터 의미와 기술 제약을, 실제 권한 책임자는 허가 절차와 책임 경계를 확인합니다. 어느 한 역할이나 AI가 다른 역할의 확인을 대신하지 않습니다.
  3. 팀이 다음 선택과 이유를 남깁니다. 빠진 근거를 조사할지, 해결책을 탐색할지, 준비된 문제를 기술 조사로 넘길지 정합니다. 받는 사람이 다음 질문과 확인 역할을 설명할 수 있어야 합니다. 여기서는 인계 파일이나 완료 상태를 만들지 않습니다.

문장 수정의 예: “요구사항이 완성됐으니 개발한다”에서 “수업 초안은 작성했지만 실제 QA 관찰과 권한 확인이 없어 보류한다”로 바꿉니다. 멈춤의 근거는 문서 품질이 아니라 독립적인 실제 조사와 책임자의 확인이 빠져 있다는 점입니다.

실제 문제 공간 종료의 확인

  • 방법 1–3의 완료 상태와 실제 기록이 일치해야 합니다.
  • 코칭 상태, 산출물, 원문 근거, 빠진 산출물을 함께 확인합니다.
  • 제약·가정의 출처와 신뢰 수준을 표시합니다.
  • 미확인·충돌을 사용자에게 드러내고 보완 또는 인계 여부를 선택하게 합니다.

공식 측면 인계의 수신 대상은 rpi-research입니다. 이후 모든 RPI 단계를 언제나 의무적으로 수행해야 한다고 이 강의에서 일반화하지 않습니다. 인계는 BRD나 요구사항 승인도 아니고 구현 허가도 아닙니다.
