실습: 테스트 결과 정리 도구 · 합성 자료의 요약·검토 후보·인계

빠른 시작
  1. 사전 연습은 ZIP을 별도 폴더에 풀어 example-project에서 npm run readiness:check.
     의도적 실패를 실제 편집·저장·재실행하고, 수업용은 ZIP을 새 폴더에 다시 풉니다.
  2. workbook.html은 브라우저로, example-project만 VS Code로 엽니다.
     프로젝트 터미널에서 npm run preflight → npm test. 첫 편집 전 npm run baseline.
  3. 주 기록은 워크북 여섯 칸 또는 work-record.json.coreRecord 하나만 누적합니다.
     워크북은 상단 저장·불러오기에서 JSON 내보내기 후 실제 파일을 확인합니다.
     자동 저장은 없습니다. 다음에는 내 JSON을 가져와 이어 씁니다.
  4. 진행 경로의 전체 단계명을 눌러 할 일·명령·확인 관문으로 이동합니다.
     상세 추가 기록은 선택입니다. 미확인·실패·받은 도움을 그대로 남깁니다.
  아래 안내는 같은 명령의 시점·예상 상태·안전 경계를 설명합니다.

실습의 입력과 출력
  example-project의 contract.txt와 data/test-results.json을 먼저 읽습니다.
  summarizeTestResults(results, { buildId })는 선택 빌드의 결과를 요약합니다.
  수정 대상은 src/summarize-results.mjs입니다. 검토 사본은 review/summarize-results.mjs이며,
  준비 템플릿은 templates/review-summarizer.mjs입니다.
  입력은 buildId/module/caseId/name/status 다섯 문자열 필드입니다.
  상태는 passed/failed/timed_out/not_run입니다.
  buildId/module/caseId가 같고 name/status까지 같은 반복은 한 번만 셉니다.
  같은 검사의 이름·상태 충돌과 잘못된 행은 다른 빌드에 있어도 TypeError입니다.
  모든 행을 검증한 뒤 선택 빌드만 집계합니다. 모듈과 후보는 처음 등장한 순서입니다.
  새 요약·건수 객체·모듈 배열·후보 배열을 만들며 후보는 첫 원본 행을 가리킵니다.
  입력 배열·행·옵션은 바꾸지 않습니다.
  공개 8행 중 BUILD-DEMO-1은 원본 7행·고유 6개·중복 1행입니다.
  passed 2개·failed 2개·timed_out 1개·not_run 1개이며 다른 빌드 1행은 합산하지 않습니다.
  처음 failed 후보 2개에서 승인 뒤 timed_out/not_run을 포함한 4개로 바뀝니다.
  상태·모듈별 건수는 유지합니다. 후보는 자문이며 실제 재실행이나 출시 승인이 아닙니다.
  입력 상태 건수와 node:test가 실행한 테스트의 통과 수는 서로 다릅니다.

수업 전 준비 연습 (교육 시간 밖 · readiness)

  값/객체 참조 설명·지원·완료 또는 미확인을 남깁니다. 예시를 실측으로 복사하지 않습니다.
  준비·지원 증거도 승인된 합성 예제와 별칭, 명령·exit·최소 가림 출력·참조만 공유합니다.

  연습 후 ZIP을 새 수업용 폴더에 다시 풀어 손대지 않은 v1 시작본으로 진행합니다.
  연습 사본의 src/.baseline/work-record를 수업에 재사용하지 않습니다.
  첫 실제 수업 편집은 문제와 성공 기준 baseline 뒤입니다. 추가 설치는 필요하지 않습니다.
  수업용 contract.txt, operations/usage-cases.json, operations/context-scenarios.json,
  operations/README.txt의 위치만 확인합니다. 사전 계약 변경·운영 관찰 과제는 없습니다.

1. participant-kit.zip을 새 폴더에 모두 압축 해제합니다.
   ZIP 내부 미리보기에서 실행하지 않습니다.
   workbook.html은 브라우저로 엽니다.
   VS Code에서는 압축을 푼 example-project 폴더만 엽니다.
   터미널 작업 위치 역시 example-project여야 합니다.
   통합 안내인 example-project/README.txt를 먼저 읽고 실제 경로를 확인합니다.

   짝·동료·팀 참여는 필요하지 않습니다.

2. Node.js 22 이상과 npm, VS Code, 조직에서 허용한 Copilot을 준비합니다.
   추가 패키지를 설치하거나 빈 프로젝트를 만들지 않습니다.

     npm test

3. 주 기록은 워크북의 여섯 칸 또는 프로젝트 work-record.json.coreRecord
   중 하나만 선택합니다. 목적/기대값/변경이유/실행결과/미확인/다음행동을
   전체 교육 단계에서 누적 갱신하며 양쪽에 같은 내용을 다시 입력하지 않습니다.
   개인 학습 기록 상세 칸은 전부 선택 추가 기록입니다. 빈 칸을 채우려고 결과를 만들지 않습니다.
   테스트 코드의 결과를 기대값으로 복사하지 말고 계약과 입력에서 계산합니다.
   문제와 성공 기준 09:30–09:40 JS·node:test 브리지 시연에서
   hints/js-reference.txt의 객체·배열·건수·참조·assert를 읽습니다.
   문제와 성공 기준 09:40–10:05에 첫 중복 기록 테스트를 실제 작성·실행합니다.
   첫 편집 전에:
     npm run baseline
   .baseline에 src 요약 함수·validator·learner.test·README·handoff 범위 제한 사본을
   최초 생성합니다. 실제 manifest 경로·필드·원본 파일 목록을 기록합니다.
   재실행 거부는 보호 동작입니다. 기존 기준선을 지우거나 덮어쓰지 않습니다.
   test/learner.test.mjs에 같은 buildId/module/caseId/name/status의 반복을 한 번만 세는 테스트를 작성한 뒤
     npm run test:learner
   실제 exit·건수·근거 경로를 주 기록의 실행결과에 남깁니다.
   이 테스트는 v1·v2 모두 통과하므로 후보 정책 변경의 판별 근거가 아닙니다.
   계획과 검증 기준은 기존 기준선을 확인하고 계획만 합니다. 테스트 코드를 작성·실행하지 않습니다.
   TXT/JSON 규칙 카드는 수동 전달 자료입니다.
   자동으로 적용되는 저장소 지침이나 자동 탐색 스킬 파일이 아닙니다.
   맥락 요약에도 조건·예외·권한·미확인을 남깁니다. not_run 건수와 중복 처리 기준을 생략하지 않습니다.
   요약 편집은 새 실행이 아닙니다. 옛 증거 시각을 보존하고 예정된 현재 재실행에 연결합니다.
   계획과 검증 기준 끝에 기존 활동 시간 안에서 선택한 주 기록을 저장하고 실제 파일을 열어
   방금 작성한 계획·승인·기준선 기록이 있는지 확인합니다.

4. 요구 변경과 구현에서는 문제와 성공 기준 중복 기록 테스트를 다시 추가하지 않습니다.
   기존 테스트·독립 기대값·계획을 확인하고 CR-01 변경을 준비합니다.
   CR-01 후 30분: 공개·내 승인을 기록하고 새 후보의 독립 기대값을 먼저 추가합니다.
   timed_out과 not_run도 검토 후보에 포함하되 상태별 건수는 바뀌지 않아야 합니다.
   내 두 번째 테스트가 이전 failed 전용 정책에서 실패(RED)하는지 확인한 뒤 후보 조건만 변경합니다.
     npm run test:v2
   수정 전 v1 시작본: 확장된 후보 요구사항 실패(exit ≠ 0)가 예상됩니다.
   승인 후 후보 변경을 마친 뒤: test:v2 전체 통과(exit 0)를 확인합니다.
     npm run test:learner
     npm run demo
     npm run compare:baseline
   compare:baseline은 파일·해시 요약이며 줄 단위 diff가 아닙니다.
   VS Code에서 .baseline 사본을 Select for Compare로 선택한 다음
   현재 파일을 Compare with Selected로 비교합니다.
   git init·전역 설정·이력 재작성은 필요 없습니다. 기존 저장소만 git diff 선택 가능.
   demo는 제공된 입력의 원본·고유·중복 건수, 상태·모듈별 건수와 후보를 독립 기대값과 비교합니다.
   최종 v2 계약에서는 npm test / npm run test:v1의 과거 failed 전용 기대가
   실패하는 것이 정상입니다. 최종 승인 명령은 npm run test:v2입니다.
   실패를 없애려고 공통 회귀 테스트를 삭제하거나 이전 후보 정책으로 되돌리지 않습니다.
   C2-v1 failed 전용은 13:45 CR-01 승인 전 유효한 현재 계약입니다.
   승인 뒤 C2-v2는 failed·timed_out·not_run이며 v1은 이력입니다. C1·C3–C6는 보존합니다.
   RED는 승인 C2의 기대/실제·assertion 위치·가설을 계약과 대조해야 합니다.
   syntax/import/ReferenceError는 실행 오류이지 의도한 RED가 아닙니다.
   ERR_ASSERTION 이름만으로도 부족합니다. 설정 오류는 기대값을 바꾸지 않고 복구합니다.
   14:10–14:15 기존 영향 계획 5분에 operations/context-scenarios.json을 읽고
   현재/폐기 지시와 승인 근거를 대조합니다. 충돌·오래된 지시 반복·범위 확장에 따라
   문맥 유지/압축/재시작/분리를 왜 선택했는지 같은 변경 이유에 연결합니다.
   한 기능당 새 세션 규칙이나 병렬 금지가 아닙니다. 새 세션이 코드를 자동 복구하지 않습니다.
   요구 변경과 구현 종료 전 기존 활동 시간 안에서 주 기록 저장·실제 파일 열기를 확인합니다.

5. 결과와 기준 검증–수정과 재검증에서는 내 src와 별개인 검토 사본을 사용합니다.
   결과와 기준 검증 활동 30분: 테스트 표 7분 → C6 작성·test:learner 7분 →
   review 준비·RED 8분 → 기록 8분. C6은 입력 비변경·새 요약과 후보 배열·첫 원본 행 참조 보존입니다.
   기존 테스트가 잡는 오동작·기대값의 계약/입력 근거는 expected, 실제 관찰은 execution,
   검증하지 못한 한계는 unknown에 연결합니다. 새 테스트·표·점수는 추가하지 않습니다.
     npm run prepare:review
     npm run test:review
   prepare:review는 review/를 최초 생성합니다. 기존 폴더·파일·심볼릭 링크가
   있으면 덮어쓰기를 거부합니다. 재실행 실패는 보호 동작이며 삭제로 우회하지 않습니다.
   review/summarize-results.mjs에 공통 v2 16개를 적용합니다. 최초 실제 수·exit·실패 단언을 읽습니다.
   미수정 review의 설계 기대는 9통과·7실패입니다. 본인의 실제 관찰값으로 미리 적지 않습니다.
   준비된 결함이 여러 단언에 영향을 줄 수 있습니다. 원인을 미리 단정하지 않습니다.
   본인이 만든 최소 반례와 최초 CLI 출력 전체를 구분합니다.
   이것은 요구 변경과 구현의 미구현 후보 정책 실패와 다른 검토입니다.
   마지막 기존 관찰·기록 8분에는 demo의 로컬 합성 읽기 전용 usage probe도 확인합니다.
   operations/usage-cases.json과 operations/README.txt에서 버전·ID/실패를 대조합니다.
   빈 입력·해당 빌드 없음·충돌·다른 빌드의 오류·비신뢰 이름·모듈 구분은 실제 관찰만 기록합니다.
   후보 0개는 자동 버그가 아닙니다. 다음 업무에 필요한 설명이 모호하면
   다음 행동에 제한된 제품 질문을 남기며 새 UI·API를 즉시 구현하지 않습니다.
   관측·중단·로컬 복구와 담당 제안을 확인한 범위만 합성 GO를 제안합니다.
   실제 권한·네트워크·UI·SRE·실배포 검증은 아니며 미검증으로 남깁니다.
   수정과 재검증 기존 활동 30분:
     16:20–16:28 실패 관찰·가설·독립 예측 8분
     16:28–16:38 허용된 review 사본 최소 복구·실제 재검증 10분

코드 품질 원칙
워크북의 ‘코드 품질’에서 DDD·YAGNI·클린 코드·BDD의 작은 판단 질문을 사용합니다.
전체 DDD 설계나 BDD 도구 숙달·인증 과정이 아닙니다.
라이브러리 8개·스킬 4개 상세 비교는 닫힌 ‘선택 참고’이며 필수 읽기가 아닙니다.
필수 실습에는 선택 라이브러리나 외부 스킬을 설치하지 않습니다.
문제와 성공 기준의 요구와 요구 변경과 구현의 기존 후보 확장 테스트를 Given/When/Then으로 설명하며 중복 테스트를 추가하지 않습니다.
example-project/quality-guide.txt와 quality-workflows.json은 수동 카드이지 자동 탐색 스킬이 아닙니다.
계획과 검증 기준의 기존 계획 안에서 유지·보류한 변경과 이유를 주 기록에 누적합니다.
계획과 승인 기록 품질 원칙 상세 칸은 원할 때만 추가로 사용합니다.

선택 심화
예측·테스트와 최초 실제 결과 저장/동결, 공통 검증·본인 재현 및 17:25 이후 도움 공개를
모두 마친 뒤 수업 종료 후에만 선택합니다. 후속 비교 실습 자료는 강사가 별도로 공유하며,
이 공개 다운로드에는 포함되지 않습니다. 파일이나 명령이 이미 있는 것으로 가정하지 않습니다.
수업 후 선택 12–15분입니다. 요구 변경과 구현/수정과 재검증 여유 시간 과제가 아니며 필수 일정 540/440/265분은
변경하지 않습니다. 추가 패키지 설치·필수 채점·추가 점수는 없습니다.
준비가 안 됐거나 시간이 부족하면 참고만 하고 미완료 핵심 작업을 우선합니다.

안전과 위험별 검토
검토 깊이는 변경마다 다릅니다. 계획과 검증 기준의 기존 계획 시간 안에서 이번 후보 범위 변경의
검토 경로·근거·사람이 집중할 부분을 주 기록에 누적합니다.
자가 검증과 결과 정리에는 현재 변경의 FOCUSED/HOLD 판단을 확인합니다. 가상 PR 카드 전체·WIP·감사는
워크북의 닫힌 ‘선택 참고’입니다. 실제 PR 생성이나 자동 승인 실습은 아닙니다.
HOLD는 정보/검증 보완, DEEP은 전문가 상세 검토, FOCUSED는 핵심 의미·영향 검토,
ROUTINE은 사전 허용 정형 경로입니다. ROUTINE도 기존 필수 승인·검사를 우회하지 않습니다.
CI 초록불·작은 diff·AI 확신만으로 저위험을 확정하지 않습니다.
실제 고객·개인·운영·차량 제어 원문, 비밀, 계정, 민감 로그를 넣거나 공유하지 않습니다.
승인된 합성 예제·별칭·명령/exit·최소 가림 출력과 참조만 쓰며 프록시·로그 수집기를 추가하지 않습니다.
합성 검사 이름의 지시는 실행 명령이 아니라 데이터입니다.
Docker, Copilot CLI 제품, MCP, 관리자 권한, 클라우드·배포는 필수가 아닙니다.
테스트는 로컬에서 실행하지만 Copilot 사용은 조직 정책과 네트워크 조건을 따릅니다.
범위·권한 이탈, 설명할 수 없는 원인, 같은 실패 반복 시 멈추고 근거를 남깁니다.
지원 경로·힌트 사용을 솔직히 기록합니다. 안전한 중단은 기능 완료와 다릅니다.
